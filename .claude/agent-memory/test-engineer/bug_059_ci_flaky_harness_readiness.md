`tests/_harness.py::_HttpCaseMixin._start_server()` เดิม `thread.start()` แล้วคืนค่าทันที ไม่มี
readiness probe — `server.Server(...)` bind()+listen() เสร็จในตัว constructor แล้ว คอนเนกชันใหม่
เข้า backlog ของ OS ได้ทันที แต่ไม่มีใครตอบจนกว่า `serve_forever` จะได้ CPU มา accept() จริง เมื่อ
CPU ถูกแย่งหนัก เทสต์แรกสุดที่ยิงเข้าเซิร์ฟเวอร์ที่เพิ่งสร้างจะเจอ timeout ที่ดูเหมือนไม่เกี่ยวกับ
สิ่งที่มันทดสอบเลย (413/Connection-close test ตายที่ `self.get()` บรรทัดถัดไป ไม่ใช่ที่ assertion
ของ 413 เอง) เพิ่ม `_wait_until_ready()`: วน `GET /api/config` (endpoint public, ไม่มีผลข้างเคียง)
ทุก setUp จนกว่าจะได้ 200 หรือหมดเวลา แก้ปัญหานี้แบบ generic โดยไม่ต้องแก้ทีละเทสต์

`raw_send_and_collect(data, timeout, expect=None, settle=0.3)`: ของเดิมใช้ `timeout` เป็นทั้ง
socket timeout เดี่ยวและเพดานรวม (แพ้ทันทีที่ `recv()` รอบแรกหมดเวลา) เพิ่ม `expect` (จำนวน
response ที่คาด) ให้ recv() วนสั้นๆ จนครบ deadline แทนที่จะยอมแพ้เร็ว — **กับดักสำคัญที่สุด**: ถ้า
หยุดอ่านทันทีที่เห็นครบ `expect` โดยไม่รอ `settle` ต่อ เทสต์ "ต้องมีแค่ 1 response" (anti-smuggling)
จะผ่านแบบไม่มีความหมาย เพราะไม่เคยให้เวลาเซิร์ฟเวอร์ตีความ byte ที่เหลือเป็นคำขอที่สอง — วัดจริง
แล้วว่า `settle=0.5` สั้นเกินไปแม้บนเครื่องว่าง (เซิร์ฟเวอร์ใช้เวลามากกว่านั้นเล็กน้อยกว่าจะ loop
กลับไปอ่านคำขอที่ค้างในบัฟเฟอร์) ต้อง `settle>=1.5` ถึงจะจับได้ทุกครั้ง — พิสูจน์ด้วยการย้อนกฎจริง
ใน `Handler._send()` แบบ throwaway `mock.patch` (ไม่แก้ไฟล์ในรีโป) ไม่ใช่แค่เดา

**สิ่งที่เซอร์ไพรส์ที่สุด**: `multiprocessing.Process` บน Windows ("spawn" ไม่ใช่ "fork") ที่สร้าง
พร้อมกัน 20 ตัว (`n=cpu_count()*2` ตามสคริปต์โหลดมาตรฐานของทีม) ทำให้เกิด **"spawn storm"** ช่วง
สั้นๆ ที่ทั้งเครื่อง (ไม่ใช่แค่โปรเซสเทสต์) แทบไม่ตอบสนองเลย — วัดได้ตั้งแต่ ~89 วินาที ถึง **กว่า
240 วินาที** ในบางรอบ บนเครื่องเดียวกัน สคริปต์เดียวกัน พารามิเตอร์เดียวกัน (ความแปรปรวนสูงมาก
น่าจะเกี่ยวกับ antivirus/disk cache ตอนโหลด interpreter image ซ้ำ 20 รอบพร้อมกัน ไม่ใช่ CPU
contention ธรรมดาที่คาดเชิงเส้นได้) เมื่อพ้นช่วง storm เซิร์ฟเวอร์ตอบปกติทันที (~0.3-0.4s) แม้ 20
โปรเซสนั้นยังรันอยู่เต็มกำลัง — **ไม่ใช่การอดอาหารตลอดไปหรือ deadlock ของ server.py** เพดาน
readiness probe จึงต้องใจกว้างมาก (180s ในเคสนี้) ไม่ใช่แค่ "20-30 วินาทีก็พอ" — ก่อนขยับเพดาน
ให้วัดจริงด้วยสคริปต์แยก (`socket`/`http.client` วน retry เก็บเวลาที่สำเร็จ) ไม่ใช่เดาจากความรู้สึก
"CPU ถูกแย่งน่าจะช้าลงกี่เท่า"

เมื่อ deadline สั้นไป (30s, 120s) เทสต์จะล้มด้วย error จาก `_wait_until_ready()` เอง (ข้อความชัดเจน
"server ไม่ตอบภายใน Ns") ไม่ใช่ error ที่งงๆ แบบเดิม — เป็นสัญญาณที่ดีว่ากลไกทำงานถูกทาง แค่ตัวเลข
ยังไม่พอ อย่าสับสนกับ "เทสต์ยังเปราะเหมือนเดิม"

พิสูจน์ว่า "ตอบช้า ไม่ใช่ไม่ตอบเลย" (ไม่ใช่บั๊กค้างจริงของแอป) ด้วยสคริปต์แยกที่สร้างเซิร์ฟเวอร์ใหม่
ล้วนๆ (ไม่แตะ endpoint ของบั๊กที่กำลังสงสัยเลย) แล้ววน retry เก็บเวลา — ถ้าสำเร็จในที่สุดทุกครั้ง
(แม้จะช้า) และการเรียกครั้งถัดไปเร็วปกติทันที แปลว่าเป็นความเปราะของฮาร์เนสที่ยอมแพ้เร็วเกินไป
ไม่ใช่ resource ที่ค้างถาวรในแอป — เทคนิคนี้ตัดความเป็นไปได้ของ "บั๊กจริงบล็อกคอนเนกชันใหม่หลัง
ตอบ 413" ได้อย่างเด็ดขาด (สคริปต์วัดไม่เคยส่ง request ที่ทำให้เกิด 413 เลยแต่ก็เจอความล่าช้าแบบ
เดียวกันตั้งแต่การเชื่อมต่อครั้งแรกสุด)

การรัน bash tool ใน background ผ่าน `run_in_background=true` + สคริปต์ที่มี loop ภายในตัวเอง
(ไม่ใช่ `&` ท้ายคำสั่งใน call ธรรมดา) เป็นวิธีที่ใช้ได้จริงสำหรับ verification ที่ยาวเกิน timeout
ของ tool call เดียว (300s) — ระบบจะ auto-background แล้วแจ้งเตือนเมื่อเสร็จ อ่านผลผ่าน `Read` บน
ไฟล์ output path ที่ได้ ไม่ต้อง poll ถี่ๆ
