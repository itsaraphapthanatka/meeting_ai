The agent team files were generated there; `project_root` in `.claude/agent-team.json` points at the main checkout (`C:/project/meeting_ai`), so re-running `render.py` from a worktree needs `--out <worktree path>` or it writes into the main checkout.

## 2026-09-16 — P0 fix round (consolidated from backend-dev ×3, test-engineer, code-reviewer, security-engineer)
- `meeting_ai/web/jobs.py:28` does `from .backend import cloud, store` — a **frozen copy**. Simulating cloud mode needs FIVE patches: `backend.cloud`, `backend.store`, `jobs.cloud`, `jobs.store`, `server.store`. Patching `backend.cloud` alone flips `auth_required()` but leaves `jobs` on the file store.
- `jobs.draft(mid)` in cloud mode is `store.job_get(mid)["_spec"]` for a job of ANY status (done/running included). It is not "a draft". Any permission or upload logic built on "a draft exists" must check `job["status"] == "draft"` explicitly.
- `submit_summarize` uses job id == meeting id and `job_upsert … on conflict do update set spec = excluded.spec`: whoever may re-summarize rewrites the whole spec row. Ask "who can call this with `self.user_id is None`?" — share-edit visitors can, and they silently dropped `owner_id` until the owner-fallback fix.
- Never compare `spec.get("owner_id") == self.user_id` directly on a path a share-only visitor can reach: `None == None` is True. Use `if owner and owner == self.user_id` (pattern in `_may_write_job`).
- psycopg passes `None` untyped; write `%s::text is null` (precedent: `job_claim` uses `%s::text[]`) or Postgres raises "could not determine data type of parameter".
- SQL can be proven without a database: monkeypatch `pgstore.db.connect` with a fake context manager that records `(sql, params)`; assert placeholder count == len(params) and the expected fragments. Catches ordering bugs instantly.
- When a path is shared and mutable, the bugs "reads someone else's file" and "deletes someone else's file" come together — `_keep_debug_shot()` unlinks its sources, so a shared `/out` turned it into an evidence shredder. Check both whenever you see a shared dir.
- Release the mount before touching the path: `docker rm -f` BEFORE `rmtree`, `_prune_stages` AFTER the `docker stop` loop — and `bot._run()` swallows timeouts (`_Timeout`, rc 124), so "after stop" is not an invariant. Confirm with `docker ps` before deleting anything a container might still mount.
- The bot's WAV destination in worker/web mode is a `tempfile.TemporaryDirectory` on another filesystem (Ubuntu `/tmp` is often tmpfs): `shutil.move` is copy+unlink and can fail (ENOSPC, AV lock). Never delete the staging dir in a `finally` unless the move succeeded or the dir holds no non-empty WAV.
- A `finally` written "to keep the folder tidy" deletes irreplaceable data more often than you think. Enumerate every exception path and what is in the folder at that moment before adding cleanup.
- Fixing the list endpoint is not fixing the leak: `workers_list()` joins `jobs.title` and still served every tenant's titles through `/api/jobs` and `/api/workers`. Grep for the leaking FIELD, not just the route.
- Adding a read-side twin (`_may_read_job`) exposed that the write-side original (`_may_write_job`) used `job["id"]` where a translate job id is not a meeting id. When you add a twin, diff it against the original line by line.
- `config.py` evaluates env into class attributes at import and loads `.env` with `setdefault`; tests that change `STT_PROVIDER`/`STT_API_KEY` must set env BEFORE `import meeting_ai` (or run a subprocess). Provider routing is testable without whisper by patching `stt.local_available` / `stt.resolve`.
- `store.py` computes `INDEX_PATH` and `SETTINGS_PATH` from `WEB_DIR` once at import: patching `store.WEB_DIR` alone still writes the owner's real `index.json`. Patch all three (done in `tests/_harness.py`).
- Several agents editing one worktree concurrently: a bare `git diff --stat` includes everyone's work. Always scope with `git diff --stat -- <your files>` before reporting.
- `$TMPDIR` is empty in Git Bash on this machine (`"$TMPDIR/x"` → `/x` → permission denied). Use the absolute scratchpad path. Long heredocs (> ~5 KB) get truncated by the Bash tool — write a script file first, then run it.
- `Path.glob()` on a missing directory does not raise in Python 3.12 but has changed between versions; keep the explicit `try/except OSError`.

## 2026-09-17 — BUG-012 invite TOCTOU review
- Moving an authorisation decision later (to make it atomic) makes every branch the old early return used to skip newly reachable. In `_signup` the removed "invalid invite → 403" uncovered the `has_password()` 409, turning signup into an email-existence oracle for anyone with a junk invite string. When you delete or move a guard, list what becomes reachable and what it tells an anonymous caller.
- Splitting one UPDATE into "claim then attach" invents a new intermediate row state. Before writing a runbook query over that state, check it is distinguishable from the failure state you mean to repair — otherwise the recovery command re-opens rows that were legitimately consumed.
- Regression-testing a TOCTOU race on `tests/_harness.py` without real sleeps: put a `threading.Barrier(N)` hook in whichever `FakeStore` method the production code calls unconditionally, exactly once, immediately before the real atomic call — every request thread blocks there until all N arrive, then races into the decision together. Deterministic, no timing guesswork. And: each atomic `FakeStore` method (`claim_invite`-style) needs its *own* short-lived lock scoped to just that method body — one shared lock across several methods makes the fake serialize the whole flow by accident, so a concurrency test passes even when production code ignores the real return value (worse than no test). Verify by temporarily reverting the atomic method to always succeed and confirming the test then reproduces the ticket's negative control.
## 2026-09-17 — rate limiting (security-engineer, BUG-010 audit)
- A rate limiter that clears its counter on success is not a rate limiter: anyone with one valid account loops `limit-1` failures + 1 login forever. Proven on `/api/auth/login` (45 guesses against another account, zero 429). Keep the resettable bucket for UX, add a second per-IP ceiling that success does NOT clear.
- The rate-limit key must be a **parsed** address, never a regex shape. `^[0-9a-fA-F:.]{3,45}$` accepts `....`, `:::`, `1.2.3.4:5678` (proxies that append a port silently disable the limiter) and makes `::ffff:X` a different bucket from `X`. Use stdlib `ipaddress` and truncate IPv6 to /64 — a /128 key gives one ordinary client unlimited buckets.
- `X-Vercel-Forwarded-For` is unspoofable **only on Vercel**. nginx/Cloudflare forward that header from the client untouched, so any self-hosted box told to set `TRUST_PROXY=1` lets the caller choose its own key. Gate Vercel-specific headers on a flag that only `api/index.py` sets.
- Fail-open is a defensible choice; fail-open **silently** is not. `except Exception: return 0.0` around the Postgres counter means a forgotten `./mai db-init` leaves production with no rate limiting at all and no log line, no `/api/config` signal, nothing. Log once per process and expose the degraded state in `backend.health()`.
- Any per-IP quota is a login DoS for everyone behind one NAT/proxy (11 requests / 15 min locks the whole office, and the "success clears the bucket" escape hatch cannot fire because nobody can succeed while blocked). Leave a trickle (e.g. 1 request/60 s) open when blocked.
- New counter/queue tables need a reaper *and a call site*: `pgstore.purge_expired()` still has zero callers, so `rate_limits` rows are permanent. Grep for the call site, not the function.
## 2026-09-16 — BUG-011 body caps (code-reviewer)
- บน `http.server`: `self.rfile.read(n)` บล็อกจนครบ n ไบต์ และ `socket.settimeout()` เริ่มนับใหม่ทุก `recv` ที่ได้ข้อมูล — loop ที่เช็ค `time.monotonic() < deadline` *ระหว่าง* การอ่านจึงไม่ใช่เพดานเวลาจริง client ที่หยอดทีละไบต์ค้างเธรดได้ไม่จำกัด (พิสูจน์แล้ว) ใช้ `read1()` + ตั้ง timeout = เวลาที่เหลือใหม่ทุกรอบ
- ตั้ง `self.close_connection = True` ไม่ได้ทำให้ response มี header `Connection: close` — http.server ไม่เติมให้ ต้องส่งเอง ไม่งั้น client เก็บคอนเนกชันไว้ใช้ต่อแล้วคำขอถัดไปตาย (RemoteDisconnected)
- เพดานที่อ่านจาก `Content-Length` ข้ามได้ด้วย `Transfer-Encoding: chunked` (ไม่มี Content-Length → ถือว่า 0 → body ถูกมองข้ามทั้งก้อน) ทุกครั้งที่ใส่เพดาน body ต้องปฏิเสธ chunked ไปด้วย
- (test-engineer) ยืนยันซ้ำทั้งสามข้อของ code-reviewer ด้วยเทสต์จริง (`tests/test_bug_011_body_size_caps.py::TestBug011KnownGapsInThisFix`, `@unittest.expectedFailure`) พบเพิ่มอีกจุด: `_read_body_to()` (track upload / worker audio / live clip) ยังอ่าน `int(Content-Length or 0)` ตรงๆ ไม่ผ่าน `_content_length()` — Content-Length พังยัง 500 อยู่ที่เส้นเหล่านี้ ก่อนแพตช์ค่าคงที่ระดับโมดูล (`mock.patch.object(module, "CONST", ...)`) เพื่อจำลอง "ย้อนกลับไปพฤติกรรมเดิม" เช็คก่อนเสมอว่าโค้ดใช้ค่านั้นเป็น **default parameter** (ผูกค่าตอนนิยามฟังก์ชัน ไม่มีทางแพตช์ทีหลังได้) หรือ **global lookup ตอนเรียก** (แพตช์ได้จริง) — และถ้าเทสต์อ้างค่าคงที่นั้นมาคูณสร้างลิสต์ทดสอบ (เช่น `[...] * MAX_SEGMENTS`) ห้ามแพตช์ค่านั้นให้ใหญ่เกินจริงเด็ดขาด (พลาดมาแล้ว: แพตช์เป็น 10**9 ทำให้เทสต์พยายามจอง RAM 18 GB) แพตช์ที่ตัวฟังก์ชัน/เมธอดแทนถ้าเทสต์อ้างค่าคงที่นั้นอยู่

## 2026-09-16 — BUG-011 body caps (security-engineer)
- `meeting_ai/web/server.py` ตั้ง `protocol_version = "HTTP/1.1"` = keep-alive เปิดตลอด และ stdlib `http.server` **ไม่ถอด `Transfer-Encoding: chunked` ให้**: ทุก request ที่เราตอบกลับโดยยังไม่ได้อ่าน body จนหมด (chunked, Content-Length สั้นกว่าจริง, CL ซ้ำ, และทุก 401/403/404/405 ที่ตอบก่อนอ่าน body) จะทำให้ไบต์ที่เหลือถูก parse เป็น request ถัดไป — ยิงครั้งเดียวได้ 2 responses จริง กฎง่าย ๆ: **ตอบกลับตอน body ยังไม่ถูกอ่านหมด = ต้องตั้ง `self.close_connection = True`** (และต้องส่ง header `Connection: close` เอง มันไม่ได้มาอัตโนมัติ)
- "เพดานเวลา" ที่เขียนเป็น `deadline` ในลูป **ไม่ใช่ timeout**: `self.rfile.read(n)` เป็น `BufferedReader` ที่บล็อกจนครบ n ไบต์ และ `connection.settimeout()` นับเฉพาะช่วงที่ "เงียบ" — client ที่หยอด 1 ไบต์ทุก 0.4 วินาทีจึงตรึงเธรดได้ไม่จำกัด (วัดได้ 21.6 วินาที และต่อได้เรื่อย ๆ) ใช้ `read1()` + คำนวณ timeout ที่เหลือใหม่ทุกรอบ และจำไว้ว่า `BaseHTTPRequestHandler.timeout` เป็น `None` โดยปริยาย = ทั้งเซิร์ฟเวอร์ไม่มี socket timeout เลย
- ทดสอบพฤติกรรม HTTP ระดับโปรโตคอล (Content-Length โกหก/ไม่ใช่ตัวเลข/ซ้ำ, chunked, การตรึงคอนเนกชัน) ด้วย `http.client` ไม่ได้ เพราะมันคำนวณ Content-Length ให้เอง — ต้องใช้ `socket` ดิบ และวัด **เวลาที่เซิร์ฟเวอร์ปิดคอนเนกชัน** ไม่ใช่แค่ status/ttfb
- `float()` ของ Python รับ `"nan"`/`"1e400"` และ `json.dumps` เขียน `NaN`/`Infinity` ลงไฟล์ได้เงียบ ๆ (JSON ที่ `JSON.parse` ของเบราว์เซอร์อ่านไม่ได้) — endpoint ไหนรับตัวเลขจากผู้ใช้ ต้อง `math.isfinite()` เสมอ ไม่งั้นเรกคอร์ดนั้นพังถาวร
- Bash tool ตัด heredoc ยาว (~9 KB) ทิ้งกลางทางจนขึ้น `unexpected EOF` — เอกสาร/รายงานยาวให้ใช้ Write tool ตรง ๆ (ยืนยันอีกครั้งจากบันทึกรอบ P0)

## 2026-09-16 — BUG-011 body caps รอบ hardening ที่สอง (test-engineer, ไม่ใส่เป็นเทสต์ถาวรเพราะเรื่องเวลา)
- ตัวเลขที่ backend-dev วัดจริงหลังแก้ `_drain_rejected_body` (หยอด 1 ไบต์ทุก 0.4 วินาที): เธรดเดี่ยวจาก **21.62 วินาที → 2.03 วินาที** และ **100 คอนเนกชันพร้อมกันถูกปล่อยครบภายใน 2.59 วินาที** — ไม่ใส่เป็น wall-clock assertion ในชุดเทสต์ถาวร (จะ flake บน CI ที่โหลดไม่แน่นอน) เก็บตัวเลขไว้ที่นี่แทนให้คนตรวจย้อนหลังเทียบได้
- พิสูจน์ไม่ vacuous ของเทสต์ "1 คอนเนกชัน = 1 response" ต้องย้อน **กลไกทีละจุด** ไม่ใช่ทั้งฟังก์ชัน: ย้อนกฎเดียวใน `_send()` ("มี body_bytes แล้วต้องปิดคอนเนกชัน") ทำให้เทสต์ที่พึ่งกฎนั้นล้มแค่ 2 ใน 4 เคส ส่วนอีก 2 เคส (chunked, duplicate Content-Length) ยังผ่านเพราะมีกลไกอื่น (`_begin_body()` ปิดคอนเนกชันเองก่อนโยน exception) คุ้มครองอยู่แล้ว — ถ้าย้อนทั้งฟังก์ชันจะพิสูจน์ไม่ได้ว่าเทสต์แต่ละตัวจับกลไกที่ตั้งใจจับจริงหรือ "เผอิญผ่านเพราะกลไกอื่นช่วยไว้"
- เทสต์ "sibling function ที่เคย 500" อาจไม่ได้ถูกปกป้องโดยตัวมันเองอีกต่อไปหลังรีแฟกเตอร์ — `_read_body_to()` เปลี่ยนไปอ่าน `self.body_bytes` ที่ `_begin_body()` เช็คมาให้แล้วตั้งแต่ `_route()` (ก่อน dispatch ไปเส้นไหนด้วยซ้ำ) การปลอมแค่ `_read_body_to()` กลับไปเป็นโค้ดเดิมจึงไม่ทำให้เทสต์ล้ม (คำขอไม่มีวันไปถึงมันเลย) ต้องปลอม **สองจุดพร้อมกัน** (`_begin_body()` แบบ no-op และ `_read_body_to()` แบบเดิม) ถึงจะเห็น 500 กลับมา — เจอกลไกป้องกันซ้อนกันแบบนี้บ่อยเวลารีแฟกเตอร์ย้ายจุดตรวจ ให้ตรวจ call path จริงก่อนเชื่อว่า "ปลอมจุดที่เคยพังจุดเดียวก็พอ"
## 2026-09-16 — web-dev design-system pass (mobile-first, `web/static/`)
- `web/jobs.py`'s in-memory job dict (`_enqueue`) sets `"meeting_id": None` at creation and only
  fills it in on `done()` — in local/file mode a **running/queued** job for `process`/`summarize`
  always has `meeting_id === None`, even though the job's own `id` already equals the meeting id
  for `process`/`summarize` (`_enqueue(mid, …)`), and `f"{mid}.tr.{lang}"` for `translate`
  (`submit_translate`). Cloud mode (`pgstore`) fills `meeting_id` immediately, so behaviour differs
  by deployment mode. Anything that needs "is a job running for meeting X" (e.g. a UI streaming
  indicator) must match on **job id**, not `job.meeting_id`, to work in both modes — verify against
  `_enqueue`/`submit_summarize`/`submit_translate` before trusting either field.
- A hex color literally copied from a design spec can fail WCAG AA for filled buttons even though
  it "is" the brand color: `#FF453A` (soft red) on white text is only ~3.5:1 contrast (needs 4.5:1).
  Apple's own systemRed light/dark variants have the same problem — vivid reds near max R channel
  cap out around 3.5-3.6:1 against white/near-white regardless of exact shade. Check contrast with
  the actual luminance formula before wiring a spec hex straight into a `color: #fff` button
  background; darkening ~20% toward black (`color-mix(in srgb, red 80%, black)`) usually clears 4.5:1
  while staying visibly "the same red".
## 2026-09-17 — BUG-055 stale detail cache regression tests
- Filesystem mtime is much coarser than the loop that writes to it: on this Windows/NTFS machine, 300 back-to-back JSON writes to one file produced only 14 distinct mtimes (286/300 collided with the write before). Any code that keys a cache on mtime equality must be tested with a **tight real loop** (100-200 iterations, no `time.sleep`) — the collision reproduces itself from raw loop speed; you do not need to force it.
- To test "this must be cached once quiet" without waiting out a real quiet period, use `os.utime(path, (old, old))` to backdate a file's mtime — legitimate (real old files have old mtimes) and deterministic. Do NOT use `os.utime` to force two writes to share an *identical* mtime as a shortcut for a same-tick collision: that fakes a backward clock jump, which is a different (accepted-limitation) scenario, not the coarse-quantization race the tight loop already reproduces honestly.
- To prove a cache is still doing its job (not silently gutted to "always re-read"), `mock.patch.object(module, "_read_json", wraps=module._read_json)` and assert it's not called across N repeated reads of an unchanged, aged-past-threshold file — cheaper and more direct than counting wall-clock time.

## 2026-09-16 — code-reviewer: `$` in a Python regex is not `end of string`
- Every id/path validator in this repo is `re.match(r"^...$", value)` (`store.valid_id`, `pgstore.valid_id`, and the new `server._safe_job_id`). Python's `$` also matches **just before a trailing newline**, so `store.valid_id("20260916-120000-abcdef" + chr(10))` returns `True` (verified 2026-09-16). Ids become filenames (`WEB_DIR / f"{job_id}.{ext}"`) and a newline is a legal POSIX filename character. Use `re.fullmatch` (or the `\Z` anchor) in new validators, and always test a valid value with a trailing newline appended when you write or review one. NUL (`chr(0)`) is correctly rejected by these character classes.
- Related: when you tighten validation on an existing `/api/worker/jobs/{id}/*` callback, remember that `worker.py` reports failures through the same URL space and swallows the error (`except WorkerError: pass`) — a job whose id the new guard rejects can neither be finished nor failed, so the reaper requeues it forever. Ship a one-off cleanup for rows created while the bug was open.

## 2026-09-16 — security-engineer: BUG-044 fix audit
- **Hardening an id that a worker callback already uses strands every row already in the queue.** `worker.py` reports failure through `POST /api/worker/jobs/{id}/error` and swallows the error from *that* call, so when the server starts rejecting the id itself the job can neither finish nor fail: it stays `running`, `pgstore.jobs_reap(30)` (run from `jobs.claim()` on every worker poll) requeues it, the worker claims it again and re-runs the LLM — forever, with no `attempts` cap. Any diff that adds or tightens validation on an existing callback must answer "what about rows already in the queue?" with a claim-side reject, a detection query, and a cleanup.
- **`re.match` + `$` is not `fullmatch`**: Python's `$` also matches just before a trailing newline, so `store.valid_id("20260916-120000-abcdef" + chr(10))` is `True`. Every id/path validator in this repo is copied from that pattern (`store._ID_RE`, `pgstore._ID_RE`, and now `_JOB_SUFFIX_RE` in `server.py`). Use `re.fullmatch` or the `\Z` anchor in anything new, and test the valid value with a newline appended before believing a validation fix.
- **Proving "no file escaped" needs a diff of the data dir *and its parent***, taken before/after the run. Listing only `WEB_DIR` cannot see the exact failure mode the bug was about.

## 2026-09-16 — test-engineer: BUG-044 regression + a Windows-specific path-traversal gotcha
- **Windows resolves `..` lexically even through path segments that don't exist as real directories; POSIX does not.** `WEB_DIR / "fake_dir_that_never_existed" / ".." / ".." / "pwned.wav"` opens (and writes) successfully on this Windows box, landing one level above `WEB_DIR`'s parent — even though `fake_dir_that_never_existed` is never created on disk. On Linux, the kernel resolves path components sequentially and would fail with `ENOENT` on the missing intermediate segment before ever reaching `..`. This is *why* the BUG-044 PoC (`<mid>.tr./../../../pwned` — the `<mid>.tr.` segment is never a real directory) worked when reproduced on the owner's Windows machine: don't assume a traversal PoC that "shouldn't work" per POSIX reasoning is safe until you've checked the actual OS. Verified by temporarily monkeypatching `server._safe_job_id` back to always-`True` (simulating the pre-fix state) and watching the guarded regression test flip from blocked (400) to an actual file write with `status 200` and a `playback` path one directory above `WEB_DIR`.
- To prove a guard test is not vacuous without touching committed source: `mock.patch.object(module, "function_name", lambda *a: <old_buggy_return>)` around a fresh run of just that test (`unittest.TestSuite()` + `TextTestRunner().run(...)`), confirm it now fails for the *reason the bug describes*, then let the `with` block exit and rerun to confirm it passes again. Cheaper and safer than editing-and-reverting the real file.
- Percent-decoding order matters for tests, not just code: a wire-level payload of `%252F` becomes the *literal three characters* `%2F` after exactly one `urllib.parse.unquote()` pass (not a real `/`). A suffix allow-list regex that excludes `%` blocks this automatically — you don't need to defeat double-encoding with extra decode passes, just don't allow `%` in the charset.
