# ADR-001 — สรุปประชุมยาวโดยไม่ชน context ของ LLM (map-reduce)

- **สถานะ**: ตัดสินใจแล้ว (2026-09-18) · ทำแล้วใน `meeting_ai/summarizer.py`
- **ตั๋ว**: BACKLOG #8 — *"No transcript chunking / map-reduce → multi-hour meetings overflow the LLM context"*
- **ผู้ตัดสินใจ**: เจ้าของโครงการ · ร่างโดย architect

---

## 1. ปัญหา

`summarize()` ยัดบทถอดเสียง **ทั้งไฟล์** ลงใน user message เดียวเสมอ ไม่ว่าประชุมจะยาวแค่ไหน
เมื่อ prompt ยาวเกิน context window ของโมเดล ฝั่ง endpoint ตอบ HTTP 400 ซึ่ง `_request()`
ไม่ได้อยู่ใน `_RETRY_CODES` จึงกลายเป็น `summary_error` ทันที และ —

**ที่สำคัญกว่านั้น — มันล้มแบบถาวร** ปุ่ม "สรุปใหม่ด้วย AI" ส่ง prompt ก้อนเดิมเป๊ะ ๆ จึงได้
ผลเดิมทุกครั้ง ผู้ใช้กดกี่รอบก็ไม่มีวันได้สรุป ต่างจาก error ชั่วคราว (429/5xx) ที่กดใหม่แล้วหาย

BACKLOG #7 แก้เรื่อง **output** ถูกตัด (`finish_reason == "length"` → ขยายเพดานแล้วยิงใหม่)
ไปแล้ว แต่ **input** ที่ยาวเกินเป็นคนละเรื่องและยังไม่มีใครดูแล

### ขนาดของจริง

ไม่มีเครื่องมือนับโทเคนในโปรเจกต์ (stdlib-only) และข้อมูลจริงอยู่ใน production ซึ่งไม่แตะ
ตัวเลขข้างล่าง **อนุมานจากของที่วัดได้จริง** ไม่ใช่การเดาลอย ๆ แต่ก็ไม่ใช่การนับโทเคนจริง:

ฐานที่วัดได้ (ระหว่างทำ BACKLOG #50): ประชุมที่ใหญ่ที่สุดใน production = **149 นาที /
2,905 segment / payload ที่ส่งกลับ ~0.64 MB** (`ensure_ascii=False`)

หักโครงสร้าง JSON ต่อ segment (คีย์ + ตัวเลข + ชื่อผู้พูด ≈ 82 ไบต์ × 2,905 ≈ 238 KB)
เหลือเนื้อข้อความ ≈ 402 KB ÷ 3 ไบต์/ตัว (ไทยใน UTF-8) ≈ **133,900 ตัวอักษร**
= ราว **900 ตัวอักษรต่อนาที**

| ความยาวประชุม | ตัวอักษร | โทเคนโดยประมาณ (1–2 ตัว/โทเคน) |
|---|---|---|
| 1 ชั่วโมง | ~54,000 | 27,000 – 54,000 |
| 2 ชั่วโมง | ~108,000 | 54,000 – 108,000 |
| 3 ชั่วโมง | ~162,000 | 81,000 – 162,000 |

ช่วงโทเคนกว้างเพราะ tokenizer ส่วนใหญ่ครอบคลุมภาษาไทยไม่ดี — ภาษาไทยกินโทเคนต่อตัวอักษร
มากกว่าอังกฤษหลายเท่า **สรุปคือ: ประชุม 2 ชั่วโมงเกิน context 32k แน่ ๆ และประชุม 3 ชั่วโมง
เข้าใกล้หรือเกิน 128k ได้** ค่าเริ่มต้นของโปรเจกต์คือ `LLM_MODEL=gemma-4-12b` บน endpoint
ของเจ้าของ ซึ่งเอกสารขนาด context ไม่ได้อยู่ในโปรเจกต์ จึง **ต้องไม่ออกแบบโดยอิงตัวเลขนั้น**

## 2. สิ่งที่ตัดสินใจ

**map-reduce แบบมีเงื่อนไข: แบ่งเป็นก้อนตามบรรทัดเมื่อยาวเกินงบตัวอักษร → สรุปย่อยแต่ละก้อน →
เอาบันทึกย่อยมารวมด้วยเทมเพลตเดิม** และ **ถอยไปใช้ทางนี้อัตโนมัติเมื่อยิงตรงแล้วโดนปฏิเสธ**

### 2.1 เกณฑ์ตัดสินใช้ "ตัวอักษร" ไม่ใช่ "โทเคน"

`LLM_CHUNK_CHARS` (ค่าเริ่มต้น 24,000) — ต่ำกว่านี้คือยิงครั้งเดียวเหมือนเดิมทุกประการ

เหตุผล: นับโทเคนให้ตรงต้องมี tokenizer ของโมเดลนั้น ซึ่งแปลว่าเพิ่ม dependency หนัก
(`tiktoken`/`transformers`) เข้าโปรเจกต์ที่ตั้งใจเป็น stdlib ล้วน **และก็ยังผิดอยู่ดี**
เพราะ endpoint เปลี่ยนโมเดลได้จาก `.env` โดยโค้ดไม่รู้ ตัวอักษรนับได้ฟรี แม่นยำ
และคาดเดาได้ ส่วนความไม่แน่นอนของอัตราส่วนตัวอักษร→โทเคน จัดการด้วยข้อ 2.4

24,000 ตัวอักษร ≈ 12,000–24,000 โทเคน + เทมเพลต (~1,500 ตัว) + งบ output 4,000 โทเคน
จึงยังอยู่ในกรอบของโมเดล 32k ที่เล็กที่สุดที่น่าจะเจอ ประชุม 149 นาทีจะถูกแบ่งเป็น ~6 ก้อน

### 2.2 ขั้น map — สกัด "ข้อเท็จจริง" ไม่ใช่ "สรุปย่อย"

แต่ละก้อนถูกขอให้คืน **บันทึกประเด็น** (ใครพูดอะไร ตกลงอะไร ใครรับงานอะไร คำถามที่ค้าง)
ไม่ใช่สรุปตามเทมเพลต เพราะถ้าให้แต่ละก้อนสรุปตามเทมเพลต จะได้ "TL;DR" หกอันมาต่อกัน
ซึ่งรวมกลับเป็นสรุปเดียวที่ดีไม่ได้ ข้อเท็จจริงดิบรวมง่ายกว่าและไม่บีบอัดซ้ำสองชั้น

### 2.3 ขั้น reduce — ใช้ทางเดิมทั้งเส้น

บันทึกย่อยทั้งหมดถูกต่อกันแล้วส่งเข้า `USER_TEMPLATE` **ตัวเดียวกับที่ประชุมสั้นใช้** ผลคือ
เทมเพลต (`general`/`oneonone`/`sales`/…), `target_lang` (BACKLOG #9) และกติกาเรื่องชื่อผู้พูด
ทำงานเหมือนเดิมโดยไม่ต้องดูแลสองทาง

### 2.4 ถอยอัตโนมัติเมื่อยิงตรงแล้วไม่ผ่าน

งบตัวอักษรเป็นการประมาณ มันผิดได้ — ภาษาที่กินโทเคนมากกว่าไทย หรือโมเดล context เล็กกว่าที่คิด
ดังนั้นถ้ายิงแบบก้อนเดียวแล้วได้ HTTP 4xx (ที่ไม่ใช่ปัญหาสิทธิ์) **ให้ลองทาง map-reduce หนึ่งครั้ง**
ก่อนจะยอมแพ้

ตั้งใจ**ไม่**อ่านข้อความ error เพื่อดูว่า "ใช่ context เกินไหม" เพราะข้อความนั้นต่างกันไปตาม
ผู้ให้บริการและเปลี่ยนได้ทุกเมื่อ การจับคำจะกลายเป็นจุดพังที่ไม่มีใครเห็น ราคาของการเดาผิดคือ
ยิงเพิ่มหนึ่งชุดที่ก็จะล้มเหมือนกัน ซึ่งถูกกว่าการ "ล้มถาวรทั้งที่แก้ได้"

## 3. ผลที่ตามมา

### ได้

- ประชุมยาวสรุปได้ แทนที่จะล้มถาวรและกดใหม่กี่ครั้งก็ไม่หาย
- ประชุมสั้น (ส่วนใหญ่) ไม่เปลี่ยนอะไรเลย — prompt เดิม จำนวนการเรียกเดิม ค่าใช้จ่ายเดิม
- ไม่ต้องเพิ่ม dependency ใด ๆ

### เสีย / ต้องยอมรับ

- **ค่าใช้จ่ายเพิ่มตามความยาว**: ประชุม 149 นาทีเปลี่ยนจาก 1 การเรียก เป็น ~7 (6 map + 1 reduce)
  แลกกับการที่เดิมได้ 0 สรุป
- **เวลานานขึ้น**: ขั้น map ทำทีละก้อนแบบเรียงกัน (ไม่ขนาน — ดูข้อ 4.4)
- **คุณภาพเปลี่ยน**: ข้อมูลผ่านโมเดลสองชั้น รายละเอียดปลีกย่อยในก้อนเดียวอาจหายตอนรวม
  ส่วนที่คุมไว้คือให้ขั้น map เก็บ "ใครรับงานอะไร" เป็นรายการตรง ๆ ซึ่งเป็นส่วนที่ผู้ใช้ใช้จริงที่สุด
- **เกณฑ์เป็นค่าคงที่เดา ๆ**: `LLM_CHUNK_CHARS` ปรับได้ใน `.env` ถ้าโมเดลที่ใช้มี context ใหญ่
  ตั้งให้สูงขึ้นจะได้สรุปที่ดีกว่าและถูกกว่า

## 4. ทางเลือกที่พิจารณาแล้วไม่เอา

### 4.1 ตัดบทถอดเสียงให้สั้นลงเฉย ๆ

ง่ายที่สุดและผิดที่สุด: ผู้ใช้จะได้สรุปที่ดูสมบูรณ์แต่ **ไม่มีครึ่งหลังของประชุม** โดยไม่มีอะไรบอก
สรุปที่ผิดแบบเงียบ ๆ แย่กว่าไม่มีสรุป

### 4.2 นับโทเคนจริงด้วย tokenizer

แม่นกว่าแต่เพิ่ม dependency หนักเข้าโปรเจกต์ที่ตั้งใจเป็น stdlib ล้วน (`tiktoken` ~2 MB +
ไฟล์ vocab, `transformers` หนักกว่ามาก) และยังผิดได้อยู่ดีเมื่อ `.env` เปลี่ยนโมเดล
เก็บไว้เป็นทางเลือกถ้าวันหนึ่งพบว่าเกณฑ์ตัวอักษรพลาดบ่อย

### 4.3 ให้ก้อนซ้อนกันเล็กน้อย (overlap)

กันหัวข้อที่ถูกตัดกลาง แต่สร้างของซ้ำในบันทึกย่อย ซึ่งกลายเป็น action item ซ้ำในสรุปสุดท้าย
ได้ การแบ่งทำที่ **ขอบ segment** (คือจุดที่คนหยุดพูด) อยู่แล้ว จึงไม่ได้ตัดกลางประโยค
เปิดไว้ทำทีหลังถ้าเห็นปัญหาจริง

### 4.4 ยิงขั้น map แบบขนาน

เร็วขึ้นหลายเท่า แต่ `runner.HEAVY_LOCK` บีบให้ทำงานหนักทีละงานอยู่แล้ว และการยิง 6 request
พร้อมกันไปที่ endpoint เดียวเสี่ยงโดน 429 ซึ่งจะทำให้เรื่องยุ่งกว่าเดิม (ต้อง backoff รายก้อน)
ทำแบบเรียงกันไปก่อน วัดแล้วค่อยว่ากัน

### 4.5 สรุปแบบสะสมทีละก้อน (refine)

ส่ง "สรุปที่มีอยู่ + ก้อนถัดไป" วนไปเรื่อย ๆ ใช้ context น้อยกว่า map-reduce แต่ผลขึ้นกับลำดับ
มาก และของที่อยู่ต้นประชุมถูกบีบอัดซ้ำทุกรอบจนจาง — ท้ายประชุมจะเด่นกว่าต้นประชุมอย่างไม่มีเหตุผล

## 5. สิ่งที่ยังไม่รู้ และจะรู้ได้อย่างไร

1. **context window จริงของ `gemma-4-12b` บน endpoint นี้** — ไม่มีเอกสารในโปรเจกต์
   วิธีรู้: ยิง prompt ที่รู้ขนาดแล้วดูว่าจุดไหนเริ่ม 400 (เสียค่า API เล็กน้อย)
   ถ้ารู้แล้วค่อยตั้ง `LLM_CHUNK_CHARS` ให้ใหญ่ที่สุดเท่าที่ปลอดภัย = ถูกลงและคุณภาพดีขึ้น
2. **อัตราส่วนตัวอักษรไทย → โทเคนของโมเดลนี้** — วัดได้จากฟิลด์ `usage` ที่ผู้ให้บริการส่งกลับ
   ถ้าเปิด `stream_options.include_usage` ตอนนี้ `_stream_chat()` ยังไม่ได้อ่านค่านั้น
   บันทึกไว้สักช่วงหนึ่งจะได้ตัวเลขจริงแทนช่วง 1–2 เท่าที่ใช้อยู่
3. **คุณภาพสรุปที่ผ่าน map-reduce เทียบกับก้อนเดียว** — ยังไม่ได้เทียบกับของจริง เพราะการ
   ทดสอบต้องยิง LLM จริงด้วยบทถอดเสียงจริง ซึ่งเป็นทั้งค่าใช้จ่ายและข้อมูลส่วนบุคคลของผู้ใช้
   ควรให้เจ้าของลองกับประชุมของตัวเองหนึ่งครั้งแล้วบอกว่าใช้ได้ไหม
