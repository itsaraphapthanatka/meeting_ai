- **สถานะ**: **ยอมรับแล้ว · ทำฝั่งหลังบ้านแล้ว 2026-09-20** (ยังไม่มีหน้าเว็บ) — ข้อ ❓ ตัดสินตามตารางใน §5 แล้ว ดู `tests/test_backlog_54_ask_backend.py`

- **ต่อจาก**: [ADR-001](ADR-001-transcript-chunking.md) (ตัวเลขขนาดบทถอดเสียงใช้ร่วมกัน)

## 1. ปัญหา

ตั๋วบอกว่า *"chips อย่าง 'Summarize action items' และ 'What was decided?' ต้องการ endpoint
สำหรับคำถามอิสระ"* — **ตรวจแล้วข้ออ้างนี้ผิดครึ่งหนึ่ง**

### 1.1 ชิปสองใบที่ตั๋วยกมา ไม่ต้องใช้ LLM เลย

สรุปที่ระบบผลิตอยู่แล้วมีหัวข้อพวกนี้อยู่ในตัวมันเอง (นับจาก `summarizer.TEMPLATES` ทั้งห้า):

| เทมเพลต | จำนวนหัวข้อ | หัวข้อ "สิ่งที่ต้องทำต่อ" | หัวข้อ "ตกลงอะไรกัน" |
|---|---|---|---|
| `general` | 5 | `## 📋 สิ่งที่ต้องทำต่อ (Action Items)` | `## ✅ ข้อสรุป / มติที่ตกลงกัน` |
| `oneonone` | 6 | `## 📋 สิ่งที่ต้องทำต่อ (Action Items)` | — |
| `sales` | 6 | `## 🤝 ขั้นถัดไปที่ตกลงกัน` | `## 🤝 ขั้นถัดไปที่ตกลงกัน` |
| `interview` | 7 | `## 📋 ขั้นถัดไป` | — |
| `standup` | 4 | `## 📋 สิ่งที่ต้องทำต่อ (Action Items)` | — |

ทั้งห้าเทมเพลตผลิต**ตารางเดียวกันเป๊ะ** (`| งานที่ต้องทำ | ผู้รับผิดชอบ | กำหนดเสร็จ |`) ต่างกันแค่
ชื่อหัวข้อที่ครอบมัน ดังนั้น

- ชิป **"Summarize action items"** = เลื่อนไปที่เช็กลิสต์ของ [PRD #53](../product/PRD-structured-action-items.md)
  ไม่ใช่การเรียก LLM · การเรียก LLM ซ้ำเพื่อสรุปสิ่งที่พิมพ์อยู่บนหน้าจอแล้ว คือการจ่ายเงินและ
  รอครึ่งนาที เพื่อผลลัพธ์ที่**แย่กว่า**ของเดิม (สรุปของสรุป = บีบอัดสองชั้น เพี้ยนมากกว่า
  ด้วยเหตุผลเดียวกับที่ `_resummarize` เลือกสรุปจากบทถอดเสียงตรง ๆ ไม่ใช่แปลจากสรุปไทย)
- ชิป **"What was decided?"** = เลื่อนไปที่หัวข้อมติ — แต่ **มีแค่ `general` กับ `sales`**
  ที่มีหัวข้อนี้ ชิปนี้จึงต้องผูกกับเทมเพลตของการประชุม ไม่ใช่โผล่เสมอ ไม่งั้นบน `standup`
  มันจะชี้ไปที่ความว่างเปล่า

### 1.2 ของจริงที่ยังไม่มี คือคำถามที่ผู้ใช้พิมพ์เอง

*"ลูกค้าติดเรื่องราคาตรงไหน"*, *"ใครรับปากว่าจะส่งภายในศุกร์"*, *"ตอนคุยเรื่อง SLA พูดว่าอะไร"*
— คำถามพวกนี้ตอบจากสรุปไม่ได้ ต้องกลับไปที่บทถอดเสียง และวันนี้ไม่มีเส้นทางไหนรับได้เลย:
`resummarize` รับได้แค่ `lang` ในบัญชีขาว และ `translate` รับได้แค่ภาษาปลายทาง

### 1.3 ขนาดของจริง

ใช้ตัวเลขชุดเดียวกับ ADR-001 (อนุมานจากประชุมใหญ่สุดใน production: 149 นาที / 2,905 segment
/ payload ~0.64 MB → ~133,900 ตัวอักษร ≈ **900 ตัวอักษรต่อนาที**):

| ความยาวประชุม | บทถอดเสียง | เทียบงบ `LLM_CHUNK_CHARS` (24,000) |
|---|---|---|
| 15 นาที | ~13,500 ตัว | ยิงครั้งเดียวพอ |
| **27 นาที** | **~24,000 ตัว** | **เส้นแบ่ง** |
| 60 นาที | ~54,000 ตัว | ~3 ก้อน |
| 149 นาที | ~133,900 ตัว | ~6 ก้อน |

**ประชุมยาวเกิน ~27 นาที ตอบคำถามด้วยการยิงครั้งเดียวไม่ได้** และประชุมงานส่วนใหญ่ยาวเกินนั้น
นี่คือเหตุผลที่ฟีเจอร์นี้ไม่ใช่ "เพิ่ม endpoint บาง ๆ"

## 2. สิ่งที่ตัดสินใจ

### 2.1 ชิปสำเร็จรูป ≠ ถาม-ตอบ — แยกกันคนละเรื่อง

ชิปที่คำตอบอยู่ในสรุปอยู่แล้ว เป็นงานของหน้าเว็บล้วน (เลื่อนไปที่หัวข้อ / เปิดเช็กลิสต์ #53)
**ห้ามหลอกผู้ใช้ว่ากำลังคิด** ในเมื่อไม่ได้คิด และห้ามคิดค่า LLM กับมัน

### 2.2 คำถามอิสระได้ **endpoint ใหม่** ไม่ใช่เทมเพลตของ `resummarize`

`POST /api/meetings/{id}/ask` body `{"question": "..."}` เหตุผลที่ไม่ยัดเข้า `resummarize`
มีสามข้อ และแต่ละข้อลำพังข้อเดียวก็ปิดประตูแล้ว:

1. **`resummarize` เขียนทับ `summary` ของการประชุม** (`apply_result` → `store.set_summary`)
   คำตอบของคำถามไม่ใช่สรุปของการประชุม ถ้ามันไปนั่งในช่องนั้น สิ่งที่ผู้ใช้เสียคือสรุปจริง
   — ความล้มเหลวคลาสเดียวกับที่ [PRD #53](../product/PRD-structured-action-items.md) เตือนไว้
2. **job id ของ `resummarize` ภาษาไทยเท่ากับ id การประชุม** (`submit_summarize`) ถามสองคำถาม
   พร้อมกันจะกลายเป็นงานเดียว เพราะ `_enqueue` upsert ด้วย id · และรูป `<mid>.sum.<lang>`
   ก็ใช้ไม่ได้ เพราะ `lang` เป็นบัญชีขาว 5 ค่า (`th en ja zh ko`) ส่วนคำถามเป็นข้อความอะไรก็ได้
3. **`template` เป็นคีย์ในบัญชีขาว** ที่ถูกเก็บลงคอลัมน์ `meetings.template` และมีผลกับการสรุป
   ครั้งต่อ ๆ ไป · คำถามครั้งเดียวไม่ควรเปลี่ยนชนิดของการประชุมอย่างถาวร

### 2.3 เป็น "งาน" (`kind = "ask"`) ไม่ใช่การเรียกแล้วรอคำตอบ

`vercel.json` ตั้ง `maxDuration: 60` ส่วน `summarizer._chat()` ตั้ง timeout ตั้งต้น **300 วินาที**
และประชุม 149 นาทีต้องยิงราว 7 ครั้ง — การเรียกแบบรอคำตอบจึงชนเพดาน 60 วินาทีแน่นอน
ไม่ใช่ "อาจช้า"

ทำเป็นงานแล้วได้ของเดิมมาทั้งชุดโดยไม่ต้องเขียนใหม่: คิว, `claim` แบบ atomic,
`attempts`/`MAX_ATTEMPTS`, `jobs_reap`, และ **หน้าเว็บ poll ทุก 1.5 วินาทีอยู่แล้ว**
(`POLL_MINE_MS` ใน `app.js`) จึงไม่ต้องมี transport ใหม่ ไม่ต้องมี SSE ไม่ต้องมี WebSocket

**ราคาที่จ่าย**: งาน `ask` ต้องรอ worker มารับ ทั้งที่ LLM เป็น HTTP endpoint ระยะไกล
(`config.llm_base_url`) ไม่ต้องใช้ GPU เลย — worker ดับ = ถามไม่ได้ · เท่ากับ `resummarize`
วันนี้ทุกประการ จึงไม่ใช่การถอยหลัง แต่ต้องรู้ตัว (ดู 5.2)

### 2.4 job id ใหม่ทุกคำถาม: `<mid>.ask.<hex6>`

`safe_job_id()` ยอมส่วนท้าย `[A-Za-z0-9._-]` อยู่แล้ว จึงไม่ต้องแก้ และ `_meeting` ยังชี้กลับ
ไปที่การประชุมเดิม ทำให้ `_job_scope()` / `_may_read_job()` คุมสิทธิ์ได้เหมือนงานอื่น

**คำถามห้ามอยู่ใน id** (ยาว มีช่องว่าง มีตัวคั่น path ได้ และเป็นข้อมูลส่วนตัวที่จะไปโผล่ใน URL
กับ log) — เก็บไว้ใน `spec` ซึ่งเป็น jsonb อยู่แล้ว

### 2.5 คำตอบไม่แตะ `summary` และไม่แตะ `translations`

`translations` เป็น map ที่คีย์คือรหัสภาษา และหน้าเว็บใช้ตัวเลือก `#d-lang` ตัวเดียวกันเลือกดู
(BACKLOG #9b) · ยัดคำตอบลงไปจะทำให้คำถามกลายเป็น "ภาษา" หนึ่ง ซึ่งพังทั้งตัวเลือกและการส่งออก

ทางที่เสนอ: **คอลัมน์ `qa jsonb not null default '[]'` บนแถว `meetings`** เพิ่มด้วย
`alter table ... add column if not exists` แบบเดียวกับ `jobs.worker` และฝั่งไฟล์เก็บใน
`<id>.json` คีย์เดียวกัน (สองแบ็กเอนด์ต้องมีชื่อฟังก์ชันชุดเดียวกันตาม PROJECT-CONTEXT)

> ⚠️ **กติกาที่ห้ามลืม**: merge เข้า main = deploy ทันที แต่ **`db-init` ไม่ถูกรันให้**
> คอลัมน์ใหม่จึงยัง**ไม่มี**อยู่พักหนึ่งหลัง deploy · ทางอ่านหลัก (`store.get`, `load_detail`,
> `list`) **ห้ามพึ่งคอลัมน์นี้** ต้องอ่านแบบทนหาย และหน้า Q&A ต้องยอมว่างได้

### 2.6 บทถอดเสียงยาวเกินงบ: ตอบเป็นสองชั้น ไม่ใช่ map-reduce ของ ADR-001

map-reduce ของ ADR-001 ออกแบบมาเพื่อ**บีบอัด** (สกัดข้อเท็จจริงจากทุกก้อน แล้วรวม) การถาม-ตอบ
ต่างกัน: คำตอบมักอยู่ใน**ก้อนเดียวหรือสองก้อน** การบังคับให้ทุกก้อนตอบจะได้ "ไม่พบในช่วงนี้"
มาห้าก้อน แล้วขั้นรวมต้องมานั่งแยกว่าอันไหนคือคำตอบจริง — จ่าย 7 ครั้งเพื่อคำตอบ 1 ครั้ง

เสนอ **ชั้นที่ 1: ตอบจากสรุป** (สรุปยาวหลักพันตัว ยิงครั้งเดียวเสมอ เร็ว ถูก) แล้วให้โมเดล
ตอบกลับมาด้วยว่า *ข้อมูลพอไหม* ถ้าไม่พอจึง **ชั้นที่ 2: ค้นบทถอดเสียงแบบคำต่อคำ** หยิบเฉพาะ
ก้อนที่มีคำในคำถาม (`str.find` ธรรมดา ไม่ต้องมี dependency) ส่งเข้าไปพร้อมคำถาม

คำถามส่วนใหญ่ ("ตกลงอะไรกัน", "มีอะไรต้องทำ") จบที่ชั้นเดียว = 1 ครั้ง ส่วนคำถามที่ต้องการ
คำต่อคำจะแพงขึ้นตามจริง · **ข้อนี้คือส่วนที่มั่นใจน้อยที่สุดทั้ง ADR** — ดู 5.1

### 2.7 เพดานการใช้งานต้องผูกกับ "คน" ไม่ใช่ "IP"

`_bucket_hit(key, limit, window)` ใช้ซ้ำได้ทันที (นับในหน่วยความจำก่อน แล้วยืนยันที่ตาราง
`rate_limits` ซึ่งหลายอินสแตนซ์ของ serverless แชร์กัน) แต่ `_rate_buckets()` ตั้งคีย์จาก IP
ซึ่ง**ผิดสำหรับเรื่องนี้**: ทั้งออฟฟิศที่ออกเน็ต IP เดียวจะแย่งโควตากันเอง

คีย์ที่เสนอ: `ask:<user_id>` และสำหรับคนถือลิงก์แชร์ `ask.share:<hash ของ token>`
— **จุดนี้สำคัญกว่าที่เห็น** เพราะ `_share_may_call()` ปล่อย `POST /api/meetings/{shared id}/...`
ให้คนที่ไม่มีบัญชีเรียกได้ ถ้าลิงก์นั้นเป็นแบบ `can_edit` ใครก็ตามที่ได้ลิงก์ไปจึงยิงคำถามได้
ไม่จำกัด **โดยเจ้าของเป็นคนจ่ายค่า LLM**

### 2.8 กับดักสิทธิ์ที่ต้องแก้ตั้งแต่บรรทัดแรก

ใน `_meeting()` เขียนไว้ว่า `writing = self.command in ("PATCH", "DELETE", "POST")` แปลว่า
**เส้น POST ใหม่จะกลายเป็น "การเขียน" โดยอัตโนมัติ** คนในทีมที่อ่านได้แต่แก้ไม่ได้ และคนถือลิงก์
แชร์แบบอ่านอย่างเดียว จะถามไม่ได้ ทั้งที่การถามไม่เปลี่ยนอะไรในการประชุมเลย
ผู้ลงมือต้องตัดสินใจเรื่องนี้อย่างตั้งใจ ไม่ใช่รับมรดกมาเงียบ ๆ (ดู 5.3)

## 3. ผลที่ตามมา

### ได้

- ตอบคำถามที่สรุปตอบไม่ได้ โดยไม่ต้องให้คนไล่อ่านบทถอดเสียงสองพันกว่าบรรทัด
- ไม่มี transport ใหม่ ไม่มี dependency ใหม่ ไม่มีเธรดใหม่ — ต่อยอดของเดิมล้วน
- ชิปสองใบในดีไซน์สร้างได้**ทันที** โดยไม่ต้องรอฟีเจอร์นี้เลย (ข้อ 2.1)

### เสีย / ต้องยอมรับ

- **ค่าใช้จ่ายกลายเป็นตัวแปรที่ผู้ใช้คุม** ต่างจากวันนี้ที่หนึ่งการประชุม = สรุปหนึ่งครั้ง
  ถามได้ไม่จำกัดคือใบเรียกเก็บเงินที่ไม่จำกัด เพดานใน 2.7 จึงไม่ใช่ของเสริม
- **คำตอบผิดได้ และดูน่าเชื่อ** สรุปที่ผิดยังมีบทถอดเสียงให้ทาน แต่คำตอบสั้น ๆ ที่ลอยมาเดี่ยว ๆ
  ไม่มีอะไรให้ทาน → คำตอบ**ต้องอ้างช่วงเวลา**ที่ใช้ตอบ เพื่อให้กดไปฟังเสียงตรงนั้นได้
- ตาราง `jobs` จะโตเร็วขึ้นมาก (วันนี้ลบเฉพาะตอนลบการประชุม) — ต้องกลับมาดู ไม่ใช่ตอนนี้
- คำตอบที่เก็บไว้คือข้อมูลส่วนบุคคลอีกที่หนึ่ง ต้องหายไปพร้อมการประชุมเมื่อผู้ใช้กดลบ

## 4. ทางเลือกที่พิจารณาแล้วไม่เอา

### 4.1 ทำเป็นเทมเพลตของ `resummarize`
ตั๋วเสนอทางนี้ตรง ๆ — ไม่เอาด้วยเหตุผลสามข้อใน 2.2 · ข้อที่แรงที่สุดคือมันเขียนทับ `summary`

### 4.2 เรียกแบบรอคำตอบ (synchronous) แล้วไม่ต้องมีคิว
ชนเพดาน `maxDuration: 60` ของ Vercel (2.3) และต่อให้ประชุมสั้นพอ ก็จะได้ประสบการณ์สองแบบ
บนเส้นเดียวกัน — สั้นก็ได้คำตอบ ยาวก็หมดเวลา โดยผู้ใช้ไม่รู้ว่าทำไม

### 4.3 เก็บคำตอบใน `summary` หรือ `translations`
ทำลายของที่มีอยู่ (2.5) และสร้างปัญหาเดียวกับที่ PRD #53 อธิบายไว้ยาว

### 4.4 ค้นด้วย embeddings / vector search (RAG)
แม่นกว่าการค้นคำต่อคำมาก แต่ต้องมี endpoint embeddings, ที่เก็บเวกเตอร์ และการคำนวณ
similarity — ฝั่งเซิร์ฟเวอร์ **stdlib เท่านั้น** (`numpy` เข้ามาทาง `sherpa-onnx` ซึ่งเป็น
ของเสริมฝั่ง worker เท่านั้น) จึงเท่ากับเพิ่ม dependency บวกงานสร้างดัชนีย้อนหลังทุกการประชุม
เก็บไว้เป็นทางเลือกถ้าวันหนึ่งพบว่าการค้นคำต่อคำพลาดบ่อยจริง

### 4.5 ไม่เก็บคำตอบเลย (ถามแล้วหายไปกับหน้าจอ)
ถูกและง่ายที่สุด ไม่ต้องย้ายข้อมูลอะไรเลย — แต่ถามคำถามเดิมซ้ำ = จ่ายซ้ำ และรีเฟรชหน้าแล้ว
คำตอบหาย ซึ่งจะถูกรายงานเป็นบั๊กแน่นอน · **ถ้าเจ้าของอยากได้ของเร็วที่สุด ทางนี้คือทางที่ควร
เลือกอย่างตั้งใจ** ไม่ใช่เพราะลืมคิด

### 4.6 ถามข้ามหลายการประชุมพร้อมกัน
คนละฟีเจอร์ ต้องมีการค้นข้ามคลังก่อน ไม่อยู่ในขอบเขตนี้

### 5.1 ❓ ชั้นที่ 1 (ตอบจากสรุป) พอสำหรับคำถามจริงกี่เปอร์เซ็นต์
วัดไม่ได้จนกว่าจะมีคนถามจริง · **เสนอให้ปล่อยชั้นเดียวก่อน** แล้วนับว่าโมเดลบอก "ข้อมูลไม่พอ"
บ่อยแค่ไหน ค่อยตัดสินใจเรื่องชั้นที่สองจากตัวเลขจริง ไม่ใช่จากการเดาวันนี้

### 5.2 ❓ ให้ฝั่งเว็บเรียก LLM เองได้ไหมเมื่อคำถามสั้นพอ
`api/index.py` บันทึกไว้แล้วว่า `LLM_API_KEY` ตั้งบน Vercel ได้ "ถ้าจะให้ฝั่ง cloud สรุปเองได้ด้วย"
ถ้าตั้งไว้จริง คำถามชั้นที่ 1 (สรุปหลักพันตัว) น่าจะจบใน 60 วินาที แต่จะได้เส้นทางประมวลผล
**สองเส้น**สำหรับฟีเจอร์เดียว ซึ่งขัดกับกติกา "`runner.py` คือทางประมวลผลทางเดียว" ใน CLAUDE.md
เสนอ: **ไม่ทำ** ให้เป็นงานทางเดียว แม้จะช้ากว่า

### 5.3 ❓ ใครถามได้ — คนที่อ่านได้ หรือเฉพาะคนที่แก้ได้
การถามไม่เปลี่ยนการประชุม แต่ใช้เงิน · ถ้าเลือก "อ่านได้ = ถามได้" ต้องแก้ `_meeting()`
ให้เส้น `ask` ไม่นับเป็นการเขียน (2.8) และต้องมีเพดานต่อคนแน่นอน

### 5.4 ❓ เก็บคำตอบไว้ไหม (ต่อจาก 4.5) และเก็บนานแค่ไหน
ถ้าเก็บ ต้องมีคอลัมน์ใหม่บวกกติกา deploy-ก่อน-migrate ใน 2.5 · ถ้าไม่เก็บ ลงมือได้เร็วกว่ามาก

### 5.5 ❓ คำตอบต้องอ้างช่วงเวลาไหม
เสนอ **ต้อง** (ข้อ 3) แต่มันทำให้ prompt ซับซ้อนขึ้นและโมเดลอาจอ้างเวลามั่ว ซึ่งแย่กว่าไม่อ้าง
ต้องลองกับประชุมจริงก่อนตัดสิน
