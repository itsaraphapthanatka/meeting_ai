# ADR-003 — ส่งความคืบหน้าไปเบราว์เซอร์: SSE หรือ poll ต่อ

- **สถานะ**: ประเมินแล้ว — **ยังไม่ทำ SSE** (2026-09-22)
- **ตั๋ว**: Ideas — *"Server → browser SSE for partial summary rendering (today the browser polls every 1.5 s)"*
- **ผู้ตัดสินใจ**: เจ้าของโครงการ · ร่างโดย architect
- **ขอบเขต**: เฉพาะช่องทาง **เซิร์ฟเวอร์ → เบราว์เซอร์** · ไม่เกี่ยวกับ SSE ที่
  `summarizer.py` ใช้คุยกับ LLM อยู่แล้ว (นั่นคือ worker → LLM คนละเส้นกันคนละทิศ)

---

## 1. ของที่มีอยู่ตอนนี้ (วัดได้)

| สิ่งที่วัด | ค่า | ที่มา |
|---|---|---|
| จังหวะ poll งานของตัวเอง | 1.5 วินาที | `app.js` `POLL_MINE_MS` |
| จังหวะ poll คิวระบบ (แอดมินดูงานคนอื่น) | 10 วินาที | `POLL_SYSTEM_MS` |
| **ตอนไม่มีงานเดินอยู่** | **ไม่ poll เลย** | `ensurePolling()` ตั้ง `ms = 0` |
| จำนวน query ต่อหนึ่ง poll | 2 | `jobs.active()` + `_workers_view()` |
| เพดานเวลาของ function | 60 วินาที | `vercel.json` `maxDuration` |

**จำนวน poll ต่องานจริง** — จับจาก log ของ worker วันที่ 2026-09-20/21:

| งาน | เวลาที่ใช้ | poll โดยประมาณ |
|---|---|---|
| `bot` → สรุป | 63.6 วินาที | ~42 |
| `process` สองแทร็ก ("man") | 96.0 วินาที | ~64 |
| `process` ไฟล์ 37 นาที | 211.2 วินาที | ~141 |

คิดหยาบ ๆ ว่าประชุมหนึ่งครั้งกินราว **40–150 invocation** และจะเป็นศูนย์ทันทีที่งานจบ
ไม่มีค่าใช้จ่ายตอนเปิดหน้าเว็บทิ้งไว้เฉย ๆ ซึ่งเป็นพฤติกรรมที่ `ensurePolling()`
ตั้งใจออกแบบไว้แล้ว (BACKLOG #41 เคยแก้เคสที่แอดมินโดน poll ทุก 1.5 วิตลอดเวลา)

---

## 2. ข้อสังเกตที่เปลี่ยนคำถามทั้งหมด

เป้าหมายที่เขียนไว้ใน Ideas คือ **"partial summary rendering"** — ให้ผู้ใช้เห็นสรุป
ไหลออกมาทีละส่วนแทนที่จะรอทั้งก้อน

**แต่ LLM ไม่ได้ถูกเรียกจาก Vercel — มันถูกเรียกจากเครื่อง worker**
(`runner.py` → `summarizer.py`) ข้อความที่ไหลออกมาจึงอยู่ที่ worker ไม่ใช่ที่เซิร์ฟเวอร์
เส้นทางที่ข้อมูลต้องเดินจริงคือ

```
worker → POST /api/worker/jobs/{id}/progress → Postgres → เบราว์เซอร์
```

และช่วงสุดท้ายนั้น **เบราว์เซอร์เห็นภายใน 1.5 วินาทีอยู่แล้ว** ตอนนี้ worker ส่งแค่
`{"step": ..., "progress": ...}` (`worker.py:197`) ถ้าให้มันส่งข้อความสรุปบางส่วน
ตามมาด้วย ผู้ใช้จะเห็นสรุปไหลออกมาทันทีโดย **ไม่ต้องมี SSE เลย**

พูดอีกแบบ: SSE แก้ปัญหา "เซิร์ฟเวอร์อยากบอกเบราว์เซอร์เดี๋ยวนี้" แต่ปัญหาจริงคือ
"worker ยังไม่ได้บอกเซิร์ฟเวอร์ว่ามีอะไรให้บอก"

---

## 3. ทางเลือก

### ก. อยู่กับ polling ต่อ (ทำอะไรเพิ่มนิดเดียว)

ให้ worker ส่งข้อความสรุปบางส่วนมากับ progress · เบราว์เซอร์ที่ poll อยู่แล้วแสดงให้เลย

- แรงที่ต้องใช้: เพิ่มฟิลด์ใน payload ของ progress + ที่เก็บ + จุดแสดงผล
- ความหน่วงที่ผู้ใช้เห็น: ≤ 1.5 วินาที
- ไม่แตะสถาปัตยกรรม ไม่เพิ่มการเชื่อมต่อค้าง

### ข. ถ่วงจังหวะ poll แบบปรับตัว

1.5 วิ ในนาทีแรก แล้วค่อยยืดเป็น 3–5 วิสำหรับงานยาว — ลด invocation ของงาน 37 นาที
จาก ~141 เหลือ ~60 โดยที่งานสั้น (ซึ่งคนนั่งมองจอ) ยังลื่นเหมือนเดิม

### ค. long-poll

เซิร์ฟเวอร์ถือ request ไว้จนมีอะไรเปลี่ยนหรือครบ ~25 วินาที — ลดจำนวน request ได้จริง
แต่เจอปัญหาเดียวกับ SSE ทุกข้อในหัวข้อถัดไป เพียงแต่เบากว่า

### ง. SSE จริง ๆ บน Vercel

## 4. ทำไมยังไม่ทำ SSE

**1. "การเชื่อมต่อค้าง" ค้างได้ไม่เกิน 60 วินาที** — `maxDuration` ของ function คือ 60
`EventSource` จะต่อใหม่เองเรื่อย ๆ ซึ่งใช้งานได้ แต่แปลว่าเราไม่ได้การเชื่อมต่อถาวรจริง
เราได้ long-poll ที่มีหน้าตาเหมือน SSE

**2. ไม่มีใครผลักข้อมูลมาให้เซิร์ฟเวอร์** — Postgres ไม่ได้ผลัก event มาที่ function
(ไม่ได้ใช้ `LISTEN/NOTIFY` และบน pooler แบบ transaction mode ก็ใช้ไม่ได้อยู่แล้ว)
ตัว handler ของ SSE จึงต้อง **poll ฐานข้อมูลเอง** ในลูป — การ poll ไม่ได้หายไป
มันแค่ย้ายจาก "เบราว์เซอร์ → เซิร์ฟเวอร์" ไปเป็น "เซิร์ฟเวอร์ → ฐานข้อมูล"
ซึ่งเป็นขาที่แพงกว่าเดิม เพราะ Postgres อยู่คนละที่กับ function

**3. บิลของ serverless คิดตามเวลาที่ function เปิดอยู่** — ถือสายไว้ 60 วินาทีต่อคนต่อนาที
เทียบกับ ~40 request สั้น ๆ ที่รวมกันไม่กี่วินาที **เวลารวมที่ function เปิดอยู่เพิ่มขึ้น
ไม่ได้ลดลง** (ข้อนี้อนุมานจากโมเดลคิดเงินของ Vercel ไม่ได้วัดบิลจริง)

**4. จำนวนคอนเนกชันของ pooler** — ทุกสายที่ถืออยู่กินคอนเนกชันหนึ่งเส้นตลอดเวลา
โปรเจกต์นี้ตั้ง `prepare_threshold=None` เพราะใช้ pooler แบบ transaction mode อยู่แล้ว
การถือสายยาวสวนทางกับโหมดนั้นโดยตรง

**5. ประโยชน์ที่ผู้ใช้เห็นน้อยกว่าที่คิด** — ความหน่วงตอนนี้คือ ≤1.5 วินาที สำหรับ
"งานเดินไปถึงไหนแล้ว" ซึ่งไม่ใช่ข้อมูลที่ต้องการความเร็วระดับต่ำกว่าวินาที

**ข้อที่ไม่ใช่อุปสรรค:** การเขียน SSE เองไม่ยากและไม่ขัดกติกา stdlib-only —
ฝั่งเซิร์ฟเวอร์เป็นแค่ response ที่เขียนต่อเนื่อง ฝั่งเบราว์เซอร์มี `EventSource` ในตัว
ไม่ต้องลง npm อะไรเลย **สิ่งที่ห้ามไม่ใช่ความยาก แต่เป็นสภาพแวดล้อมที่รันอยู่**

---

## 5. ข้อเสนอ

1. **ไม่ทำ SSE ตอนนี้**
2. ถ้าอยากได้ "สรุปไหลออกมาทีละส่วน" → ทำทาง **ก.** (worker ส่งข้อความบางส่วนมากับ
   progress) ซึ่งได้ผลเดียวกันโดยไม่แตะสถาปัตยกรรม
3. ถ้าอยากลดจำนวน invocation → ทำทาง **ข.** (ถ่วงจังหวะแบบปรับตัว)

ทั้งสองข้อเป็นงานเล็กและเป็นอิสระต่อกัน ทำข้อไหนก่อนก็ได้

## 6. อะไรจะทำให้กลับมาคิดใหม่

- **ย้ายออกจาก serverless** ไปโฮสต์ที่มีโพรเซสค้างได้ (เช่นรัน `mai web` บนเครื่องจริง)
  — ข้อ 1, 3, 4 หายไปทันที เหลือแค่ต้องแก้เรื่อง `LISTEN/NOTIFY`
- ต้องการอัปเดตหลายคนพร้อมกันแบบ real-time (เช่นแก้บทถอดเสียงพร้อมกัน) ซึ่งเป็นคนละ
  ปัญหากับการรายงานความคืบหน้า และ 1.5 วินาทีไม่พอแน่นอน
- Vercel ยกเพดาน `maxDuration` ขึ้นมากจนถือสายได้เป็นสิบนาที **และ** ราคายังคุ้ม
