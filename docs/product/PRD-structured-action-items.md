# PRD — Action Items ที่ติ๊กได้ (structured action items)

- **สถานะ**: ร่าง · รอเจ้าของตัดสินใจข้อที่ทำเครื่องหมาย ❓ ไว้
- **ตั๋ว**: BACKLOG #53 · ผู้รับผิดชอบต่อ: architect → backend-dev → web-dev
- **เขียน**: 2026-09-18 · ข้อเท็จจริงทั้งหมดตรวจกับโค้ดปัจจุบันแล้ว (อ้างไฟล์ไว้ทุกจุด)

---

## 1. ปัญหา

ทุกเทมเพลตสรุป (`general`, `oneonone`, `sales`, `interview`, `standup` — ตรวจครบทั้งห้าแล้ว)
สั่งให้ LLM ผลิตตารางนี้:

```
## 📋 สิ่งที่ต้องทำต่อ (Action Items)
| งานที่ต้องทำ | ผู้รับผิดชอบ | กำหนดเสร็จ |
|---|---|---|
| ... | ... | ... |
```

แต่มันเป็น **ข้อความ Markdown ในก้อน `summary` เท่านั้น** ผลคือ

- ติ๊กว่า "ทำแล้ว" ไม่ได้ — ต้องแก้ข้อความสรุปเอง ซึ่งทำให้สรุปเพี้ยนจากสิ่งที่ประชุมพูดจริง
- ไม่มีทางรู้ว่า "ยังเหลืออะไร" โดยไม่อ่านสรุปทั้งฉบับ
- คอมโพเนนต์ **Action Item Checkbox** ในดีไซน์มือถือจึงยังไม่ถูกสร้าง — ตั้งใจไม่สร้างเพราะ
  ไม่มีข้อมูลรองรับ (ตามที่ตั๋วบันทึกไว้)

**ผู้ใช้ที่เจ็บ**: คนที่จัดประชุมแล้วต้องตามงานต่อ ซึ่งคือเหตุผลหลักที่คนใช้เครื่องมือสรุปประชุม
ตั้งแต่แรก การสรุปได้สวยแต่ตามงานไม่ได้ คือทำครึ่งเดียวของงาน

## 2. สิ่งที่ *ไม่* ใช่ปัญหา (ขอบเขตที่ไม่ทำ)

- **ไม่ทำระบบจัดการงานเต็มรูปแบบ** — ไม่มีลำดับความสำคัญ ไม่มีความคืบหน้าเป็นเปอร์เซ็นต์
  ไม่มีคอมเมนต์ต่อรายการ ไม่มีการแจ้งเตือน ถ้าต้องการสิ่งเหล่านี้ ใช้เครื่องมืออื่นที่ทำมาเพื่อสิ่งนั้น
- **ไม่ผูกผู้รับผิดชอบกับบัญชีผู้ใช้ในเวอร์ชันแรก** — ดูข้อ 6.2
- **ไม่แตะฝั่ง worker** — งานทั้งหมดอยู่ที่เซิร์ฟเวอร์กับหน้าเว็บ ไม่ต้องอัปเดตเครื่อง GPU

## 3. เรื่องที่ยากจริง ๆ ของฟีเจอร์นี้

ไม่ใช่การแยกตาราง แต่คือ **สรุปเปลี่ยนได้สี่ทาง แล้วสถานะที่ผู้ใช้ติ๊กไว้จะอยู่ที่ไหน**

| ทางที่สรุปเปลี่ยน | โค้ด |
|---|---|
| งานถอดเสียงจบ สร้างสรุปครั้งแรก | `jobs.apply_result()` → `store.create()` |
| กด "สรุปใหม่ด้วย AI" | `jobs.apply_result()` → `store.set_summary()` |
| กด "สรุปใหม่" เป็นภาษาอื่น | → `store.set_translation()` (BACKLOG #9b) |
| ผู้ใช้แก้ Markdown เอง | `PATCH /api/meetings/{id}` → `store.update(summary=)` |

ถ้าเก็บสถานะแยกแล้วจับคู่ผิด ผู้ใช้จะเสียเครื่องหมายถูกที่ติ๊กไว้โดยไม่มีอะไรเตือน
**นั่นคือความล้มเหลวที่แย่ที่สุดของฟีเจอร์นี้** — แย่กว่าไม่มีฟีเจอร์เลย เพราะคนจะเชื่อมันไปแล้ว

### ทางเลือกที่พิจารณา

| ทาง | ข้อดี | ทำไมไม่เอา |
|---|---|---|
| **A** แยกตารางตอนอ่าน ไม่เก็บอะไร | ง่ายสุด ไม่มีอะไรหลุดกัน | ติ๊กไม่ได้ = ไม่ได้แก้ปัญหา |
| **B** เก็บเป็นระเบียน แล้วซิงก์จากสรุปทุกครั้งที่สรุปเปลี่ยน โดยจับคู่ด้วยข้อความ | สถานะอยู่รอดเมื่อข้อความไม่เปลี่ยน · สรุปยังเป็นแหล่งความจริงของ "ประชุมพูดอะไร" | ถ้า LLM เรียบเรียงคำใหม่ จับคู่ไม่ได้ |
| **C** ระเบียนเป็นแหล่งความจริง สรุปเป็นแค่การแสดงผล | ไม่มีทางหลุด | สรุปใหม่ทุกครั้งต้อง merge เข้าระเบียน ซับซ้อนกว่ามาก และทำให้ "สรุปคือสิ่งที่ประชุมพูด" ไม่จริงอีกต่อไป |
| **D** ฝังรหัสซ่อนไว้ใน Markdown | จับคู่แม่น | ผู้ใช้แก้สรุปเองได้ รหัสจะพัง และข้อความสรุปที่ดาวน์โหลดไปจะมีขยะ |

### ข้อเสนอ: **ทาง B พร้อมการกระทบยอดที่มองเห็นได้**

1. แยกตารางจาก `summary` (ภาษาต้นฉบับเท่านั้น — ดู 6.1) ทุกครั้งที่ `summary` ถูกเขียน
2. จับคู่กับระเบียนเดิมด้วย **ข้อความงานที่ normalize แล้ว** (ตัดช่องว่างซ้ำ ตัดวรรคตอนท้าย
   เทียบแบบไม่สนตัวพิมพ์)
3. รายการใหม่ → เพิ่มเป็น `pending`
4. รายการเดิมที่ยังจับคู่ได้ → **คงสถานะและผู้รับผิดชอบที่ผู้ใช้แก้ไว้**
5. รายการเดิมที่จับคู่ไม่ได้:
   - ถ้ายัง `pending` → ลบทิ้งเงียบ ๆ ได้ (ไม่มีอะไรของผู้ใช้อยู่ในนั้น)
   - ถ้า **`done` แล้ว → ห้ามลบ** เก็บไว้และติดป้าย `orphan: true` แสดงในกลุ่มแยกว่า
     *"ทำแล้ว แต่ไม่อยู่ในสรุปล่าสุด"* พร้อมปุ่มลบให้ผู้ใช้ตัดสินใจเอง

ข้อ 5 คือหัวใจ: **เราไม่ลบงานที่คนติ๊กว่าทำแล้ว ด้วยการเดาของเครื่อง**

## 4. User stories และเกณฑ์ยอมรับ

เกณฑ์ทุกข้อทดสอบได้ด้วย `e2e-tester` หรือคนจริง

### US-1 — เห็นรายการที่ต้องทำโดยไม่ต้องอ่านสรุปทั้งฉบับ
*ในฐานะเจ้าของการประชุม ฉันอยากเห็นรายการงานเป็นเช็กลิสต์*

- **AC-1.1** เปิดการประชุมที่สรุปมีตาราง Action Items → เห็นรายการเป็นเช็กบ็อกซ์
  จำนวนเท่ากับจำนวนแถวในตาราง (ไม่นับแถวตัวอย่าง `| ... | ... | ... |`)
- **AC-1.2** แต่ละรายการแสดง ข้อความงาน · ผู้รับผิดชอบ · กำหนดเสร็จ ตรงกับในตาราง
- **AC-1.3** แถวที่ผู้รับผิดชอบเป็น `ไม่ได้ระบุ` แสดงเป็นช่องว่างที่กดเพิ่มชื่อได้ ไม่ใช่คำว่า
  "ไม่ได้ระบุ" (คำนั้นมีไว้บอก LLM ไม่ใช่บอกผู้ใช้)
- **AC-1.4** ประชุมที่สรุปไม่มีตาราง (หรือยังไม่มีสรุป) → ไม่แสดงส่วนนี้เลย ไม่ใช่กล่องว่าง
- **AC-1.5** ตารางในสรุปยังแสดงเหมือนเดิม — เช็กลิสต์เป็นส่วนเพิ่ม ไม่ใช่ตัวแทน
  (คนที่ดาวน์โหลดสรุปเป็น Markdown/docx ต้องยังได้ตารางครบ)

### US-2 — ติ๊กว่าทำแล้ว
- **AC-2.1** ติ๊ก → บันทึกทันทีโดยไม่ต้องกดปุ่มบันทึกแยก และอยู่รอดหลังรีเฟรช
- **AC-2.2** ติ๊กแล้วปิดเบราว์เซอร์ เปิดใหม่จากเครื่องอื่น → ยังเห็นว่าติ๊กแล้ว
- **AC-2.3** สองคนติ๊กพร้อมกันคนละรายการ → ไม่มีใครถูกเขียนทับ
- **AC-2.4** จำนวน "เหลือ n รายการ" ตรงกับจำนวนที่ยังไม่ติ๊กเสมอ

### US-3 — แก้ผู้รับผิดชอบ
- **AC-3.1** กดที่ชื่อผู้รับผิดชอบแล้วพิมพ์ทับได้ บันทึกทันที
- **AC-3.2** ชื่อที่ผู้ใช้แก้เอง **ไม่ถูกเขียนทับ** เมื่อกดสรุปใหม่แล้วข้อความงานยังเหมือนเดิม

### US-4 — สรุปใหม่แล้วของที่ติ๊กไว้ไม่หาย *(สำคัญที่สุด)*
- **AC-4.1** ติ๊กสองรายการ → กด "สรุปใหม่ด้วย AI" → รายการที่ข้อความเหมือนเดิมยังติ๊กอยู่
- **AC-4.2** รายการที่หายไปจากสรุปใหม่ **และเคยติ๊กแล้ว** → ยังแสดงอยู่ในกลุ่ม
  "ทำแล้ว แต่ไม่อยู่ในสรุปล่าสุด" พร้อมปุ่มลบ
- **AC-4.3** รายการที่หายไปและยัง `pending` → หายไปเงียบ ๆ ได้
- **AC-4.4** ผู้ใช้แก้ข้อความสรุปเองแล้วบันทึก → รายการถูกกระทบยอดด้วยกติกาเดียวกัน
- **AC-4.5** ลบตาราง Action Items ออกจากสรุปทั้งหมด → รายการ `pending` หายหมด แต่รายการ
  `done` ยังอยู่ในกลุ่มแยก

### US-5 — สิทธิ์
- **AC-5.1** คนที่แก้การประชุมไม่ได้ (`_may_write` เป็นเท็จ) → เห็นเช็กลิสต์แต่ติ๊กไม่ได้
  และ API ตอบ 403
- **AC-5.2** คนถือลิงก์แชร์แบบ `can_edit` → ติ๊กได้ ❓ *(ดู 6.3)*

## 5. ผลต่อระบบที่มีอยู่

- **โหมดไฟล์กับโหมด cloud ต้องทำเหมือนกัน** — `store.py` และ `pgstore.py` เปิดชื่อฟังก์ชัน
  ชุดเดียวกัน (ดู PROJECT-CONTEXT → Storage) ฟังก์ชันใหม่ต้องมีทั้งสองฝั่ง
- **stdlib เท่านั้น** — ตัวแยกตาราง Markdown ต้องเขียนเอง ไม่เพิ่ม dependency
  (หน้าเว็บมีตัวเรนเดอร์ Markdown ที่เขียนเองอยู่แล้วใน `app.js` แต่**ห้ามใช้ฝั่งหน้าเว็บ
  เป็นแหล่งความจริง** — ต้องแยกที่เซิร์ฟเวอร์ ไม่งั้นสองไคลเอนต์เห็นไม่ตรงกัน)
- **การส่งออก** (`web/exports.py`, md/txt/srt/vtt/docx) ยังส่งออกจาก `summary` เหมือนเดิม
  ตาม AC-1.5 — ไม่ต้องแก้ ❓ *หรือจะเติมสถานะ `[x]` ลงในไฟล์ที่ส่งออกด้วย (ดู 6.4)*
- **ข้อมูลส่วนบุคคล**: ชื่อผู้รับผิดชอบคือชื่อคนจริง อยู่ในระเบียนใหม่นี้ด้วย ต้องถูกลบไปพร้อม
  การประชุมเมื่อผู้ใช้กดลบ (เทสต์ต้องครอบข้อนี้)

## 6. สิ่งที่ต้องให้เจ้าของตัดสินใจ

### 6.1 แยกจากสรุปภาษาไหน — **เสนอ: ภาษาต้นฉบับเท่านั้น**
คำแปลมีหัวตารางที่ถูกแปลไปด้วย (`| Task | Owner | Due |`) การแยกจากคำแปลต้องรู้หัวตาราง
ทุกภาษา และจะได้รายการซ้ำข้ามภาษา เสนอให้ผูกกับ `summary` อย่างเดียว แล้วเช็กลิสต์ใช้ร่วมกัน
ทุกภาษา (งานชิ้นเดียวกันไม่ว่าจะอ่านภาษาไหน)

### 6.2 ผู้รับผิดชอบเป็นข้อความอิสระ หรือผูกกับบัญชีผู้ใช้
LLM ให้ชื่อมาแบบ "คุณสมชาย" ซึ่งเป็นชื่อผู้พูด ไม่ใช่บัญชี การผูกกับบัญชีต้องมีการจับคู่ชื่อ→ผู้ใช้
ซึ่งผิดได้และเป็นฟีเจอร์ของตัวเอง **เสนอ: v1 เก็บเป็นข้อความอิสระ** แล้วค่อยเพิ่ม `assignee_user_id`
ทีหลังถ้ามีคนขอ

### 6.3 คนถือลิงก์แชร์แบบแก้ได้ ติ๊กได้ไหม
เสนอ **ได้** เพราะการแชร์แบบแก้ได้มีไว้ให้คนร่วมประชุมมาช่วยเกลาสรุปอยู่แล้ว และการตามงาน
คือเหตุผลที่แชร์ แต่เป็นการเปิดให้คนที่ไม่มีบัญชีเขียนข้อมูลได้ จึงควรเป็นการตัดสินใจที่ตั้งใจ

### 6.4 ไฟล์ที่ส่งออกควรมีเครื่องหมายถูกไหม
เสนอ **มี** ในรูป `- [x] งาน (ผู้รับผิดชอบ · กำหนด)` ต่อท้ายตารางเดิม เพราะคนส่งออกไปเพื่อส่งต่อ
ให้ทีม แต่มันเปลี่ยนหน้าตาไฟล์ที่คนเคยชิน

### 6.5 เก็บเป็นคอลัมน์ JSON หรือตารางใหม่
คอลัมน์ JSON บนแถวการประชุม (แบบเดียวกับ `translations`) ถูกและเร็วกว่าสำหรับ v1
**แต่ถ้าวันหนึ่งอยากได้หน้า "งานของฉันทั้งหมดข้ามประชุม"** จะต้องมีตารางจริงและต้องย้ายข้อมูล
เสนอ: เริ่มด้วยคอลัมน์ JSON และบันทึกไว้ว่าอะไรคือสัญญาณที่ต้องย้าย

## 7. ลำดับการทำ

1. **backend-dev** — ตัวแยกตาราง + กติกากระทบยอด + ที่เก็บทั้งสองแบ็กเอนด์ + เส้น API
   (`PATCH /api/meetings/{id}/action-items/{index}` หรือรูปแบบที่ architect เลือก)
   พร้อมเทสต์ที่ครอบ AC-4.x ทั้งหมด **ก่อน** แตะหน้าเว็บ
2. **web-dev** — คอมโพเนนต์เช็กลิสต์ตามดีไซน์มือถือ + กลุ่ม "ไม่อยู่ในสรุปล่าสุด"
3. **e2e-tester** — เดินเส้น ติ๊ก → สรุปใหม่ → ตรวจว่าของที่ติ๊กไม่หาย

## 8. วัดผลอย่างไรว่าคุ้มที่ทำ

ไม่มีระบบเก็บสถิติการใช้งานในโปรเจกต์นี้ และไม่เสนอให้เพิ่มเพื่อเรื่องนี้ เกณฑ์จึงเป็นเชิงคุณภาพ:
**เจ้าของใช้เองกับประชุมจริงสิบครั้ง แล้วตอบได้ว่าเคยเสียเครื่องหมายถูกที่ติ๊กไว้หรือไม่**
ถ้าเคยแม้ครั้งเดียว แปลว่ากติกากระทบยอดยังไม่ดีพอ และต้องแก้ก่อนขยายฟีเจอร์
