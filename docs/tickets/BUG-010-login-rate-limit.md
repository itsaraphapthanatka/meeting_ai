# BUG-010 — `POST /api/auth/login` ไม่มี rate limit

- **Status:** fixed — รอบรีวิวที่ 1 ปิดครบทั้ง 7 ข้อ + ข้อ low (ดูหัวข้อท้ายไฟล์)
- **Severity:** P1 (security) — รายการสุดท้ายที่ยังเปิดอยู่จากรีวิว 2026-09-16 (BACKLOG #10)
- **Owner:** backend-dev
- **Created:** 2026-09-17
- **Fixed:** 2026-09-17
- **Files:** `meeting_ai/web/server.py`, `meeting_ai/web/ratelimit.py` (ใหม่), `meeting_ai/web/pgstore.py`, `meeting_ai/web/schema.sql`, `api/index.py`

## ปัญหา

`_login()` เรียก `store.verify_password(email, password)` ทันทีโดยไม่มีตัวนับใดๆ และ
`("auth","login")` อยู่ใน `PUBLIC_API` จึงยิงได้โดยไม่ต้องมี session

ผลที่ตามมามีสองชั้น:

1. **Credential stuffing** — เดารหัสผ่านได้ไม่จำกัดจำนวนครั้ง
2. **CPU/memory amplifier ที่ไม่ต้องล็อกอิน** — `_SCRYPT = {"n": 2**14, "r": 8, "p": 1}`
   (`pgstore.py:97`) กินหน่วยความจำราว 16 MB + CPU จริงต่อหนึ่งครั้ง และ `verify_password`
   ตั้งใจคำนวณ hash หลอกต่อแม้ไม่พบอีเมล (กัน timing oracle) แปลว่า request เล็กๆ ที่ไม่ต้อง
   มีบัญชีเลยซื้องานหนักของเซิร์ฟเวอร์ได้ — บน Vercel คือค่าใช้จ่าย + คิวฟังก์ชัน

## สิ่งที่ต้องได้

1. ตัดสินใจ **ก่อน** ลงมือ hash เสมอ (ก่อน `_body_json()` ด้วย จะได้ไม่อ่าน body ที่ไม่มีขอบเขต)
2. ครอบคลุมทั้งสองทรงการ deploy:
   - **self-hosted** (`mai web --cloud` โพรเซสเดียวอยู่ยาว) — ตัวนับในหน่วยความจำใช้ได้
   - **Vercel serverless** — แต่ละ invocation ไม่แชร์หน่วยความจำกัน ตัวนับใน process จึง
     "ทำงานเงียบๆ โดยไม่ได้กันอะไรเลย" ซึ่งแย่กว่าไม่แก้ เพราะ backlog จะขึ้นว่าแก้แล้ว
3. ไม่รั่วว่าอีเมลนั้นมีบัญชีจริงหรือไม่ ทั้งทาง status และเวลา
4. ผู้ใช้จริงต้องไม่ถูกล็อกถาวร

## การตัดสินใจ (และเหตุผล)

### ก) เก็บตัวนับไว้ที่ไหน — Postgres เป็นตัวจริง + หน่วยความจำเป็นชั้นหน้า

หน้าล็อกอิน **มีเฉพาะโหมด cloud** (`_auth_api` ตอบ 501 เมื่อ `backend.auth_required()` เป็นเท็จ
= โหมดไฟล์ไม่มีระบบล็อกอินเลย) แปลว่าทุกการ deploy ที่มี endpoint นี้ **มี Postgres อยู่แล้ว**
จึงใช้ตาราง `meeting_ai.rate_limits` เป็นตัวนับที่แชร์กันได้ทุก instance — ครอบคลุมทั้ง Vercel
และ self-hosted ด้วยกลไกเดียว ไม่ต้องเพิ่ม dependency (Redis/Upstash) ซึ่งผิดกติกา stdlib-only

ชั้นในหน่วยความจำ (`web/ratelimit.py`) ยังมีอยู่เพราะสองเหตุผล:
- คำขอที่ถูกบล็อกแล้วตอบได้โดยไม่ต้องแตะ DB เลย (ราคาเกือบศูนย์ — ดูหัวข้อ "พิสูจน์")
- ถ้า DB ล่ม/ตอบช้า ยังมีการจำกัดระดับโพรเซสเหลืออยู่ (fail-open ต่อ DB แต่ไม่ fail-open ทั้งหมด)

**ทรงไหนได้อะไรจริง:** self-hosted ได้ทั้งสองชั้น; Vercel ได้ชั้น Postgres เป็นหลัก (ชั้น
หน่วยความจำอาจช่วยได้บ้างเมื่อ instance ถูกใช้ซ้ำ แต่ห้ามนับว่าเป็นการป้องกัน)

### ข) คีย์ = IP ไม่ใช่อีเมล

ผูกกับ IP ของผู้เรียก (key = `login:<ip>`, `signup:<ip>`) เพราะคีย์ตามอีเมลเปิดช่องให้คนนอก
ล็อกบัญชีเหยื่อได้ตามใจ (ยิงรหัสผิดซ้ำๆ = เจ้าของตัวจริงเข้าไม่ได้) ซึ่งชนกับข้อกำหนด
"ต้องไม่ถูกล็อก" ตรงๆ และคีย์ตาม IP ตรงกับภัยหลักคือ CPU amplifier ซึ่งราคาเกิดที่
*ทุก request* ไม่ว่าอีเมลจะเป็นอะไร

**สิ่งที่ยังไม่ได้กัน (พูดตรงๆ):** credential stuffing แบบกระจาย IP (botnet/residential proxy)
ยิงบัญชีเดียวช้าๆ ยังผ่านได้ — ต้องใช้ captcha/anomaly detection ซึ่งอยู่นอกตั๋วนี้

ที่มาของ IP: Vercel เขียนทับ `x-forwarded-for` ให้เอง และมี `x-vercel-forwarded-for` ที่ปลอมไม่ได้
จึงอ่าน `x-vercel-forwarded-for` ก่อน แล้วค่อยเป็น **ตัวขวาสุด** ของ `x-forwarded-for`
(ตัวซ้ายสุดเป็นค่าที่ client ใส่เองได้) และเชื่อหัวข้อพวกนี้เฉพาะเมื่อ `Handler.trust_proxy`
เป็นจริงเท่านั้น (`api/index.py` ตั้งให้ / self-hosted หลัง nginx ตั้ง `TRUST_PROXY=1`)
ถ้าไม่ตั้ง จะใช้ `client_address` ซึ่งปลอมไม่ได้แต่จะกลายเป็นถังเดียวกันทั้งองค์กร

### ค) โควตา 10 ครั้ง / 15 นาที ต่อ IP ต่อ endpoint

- คนจริงพิมพ์รหัสผิดไม่กี่ครั้ง (ตัวจัดการรหัสผ่านลองครั้งเดียว) 10 ครั้งใน 15 นาทีจึงสูงกว่า
  การใช้งานจริงมาก แต่ยังกดงาน scrypt จาก IP เดียวเหลือ ≤ 10 ครั้ง/15 นาที
- บล็อกแค่จนหมดหน้าต่างปัจจุบัน (สูงสุด 15 นาที) **ไม่มีการล็อกถาวร** และไม่แตะสถานะบัญชี
- **ล็อกอินสำเร็จล้างตัวนับของ IP นั้นทิ้ง** — ออฟฟิศที่ออกเน็ตทาง IP เดียว (หรือ self-hosted
  หลัง proxy ที่ไม่ได้ตั้ง `TRUST_PROXY`) จึงแทบไม่มีทางชนเพดาน เพราะเพดานนับเฉพาะความพยายาม
  ที่ยังไม่มีใครสำเร็จเลยใน 15 นาที
  *แลกกับ:* คนที่มีบัญชีจริงอยู่แล้วหนึ่งใบรีเซ็ตตัวนับของตัวเองได้ → ตั๋วนี้ไม่ได้กัน "คนใน"
  เผางาน scrypt แต่กันคนนอกที่ไม่มีบัญชีเลยได้ครบ ซึ่งเป็นภัยที่ตั๋วนี้ตั้งใจปิด

### ง) `_signup` ก็ใส่ด้วย (คนละถัง)

`_signup` เป็น public เหมือนกันและเรียก `set_password` (scrypt) เมื่อรหัสเชิญผ่าน — ที่สำคัญกว่า
คือมันเปิดให้ **เดารหัสเชิญ** ได้ไม่จำกัดผ่าน `invite_email(code)` จึงใส่โควตาเดียวกันแต่แยกถัง
(`signup:<ip>`) เพื่อไม่ให้การสมัครไปกินโควตาการล็อกอินของเครื่องเดียวกัน

## ขอบเขต

- ไม่มีการเปลี่ยนพฤติกรรมอื่นของ `_login`/`_signup` (ข้อความ error เดิม, สถานะเดิม)
- ไม่แตะ BACKLOG / LEARNINGS (เจ้าของอื่นดูแล) และไม่เขียน regression test (test-engineer เป็นคนเขียน)

## สัญญา API

`POST /api/auth/login` และ `POST /api/auth/signup` เพิ่มผลลัพธ์หนึ่งแบบ:

```
HTTP/1.1 429 Too Many Requests
Retry-After: <วินาที>
{"error": "<ข้อความไทย>", "retry_after": <วินาที>}
```

ข้อความและสถานะเหมือนกันทุกกรณี ไม่ขึ้นกับว่าอีเมลนั้นมีอยู่จริงไหม (ตรวจก่อนอ่าน body ด้วยซ้ำ)
ฝั่ง client แสดง `data.error` อยู่แล้ว (`app.js:74`) จึงไม่ต้องแก้อะไรเพื่อให้ใช้งานได้

## Schema

เพิ่มท้าย `meeting_ai/web/schema.sql` (idempotent):

```sql
create table if not exists meeting_ai.rate_limits (
    key         text primary key,
    hits        integer not null default 0,
    expires_at  timestamptz not null default now()
);
```

**เจ้าของต้องรัน:** `./mai db-init` (ครั้งเดียว บน environment ที่มีล็อกอิน) — ถ้ายังไม่รัน
endpoint ล็อกอินยังทำงานปกติ แต่ชั้น Postgres จะ fail-open (เหลือแค่ชั้นในหน่วยความจำ)

## พิสูจน์ (ต้องทำให้ครบก่อนปิดตั๋ว)

1. ยิงล็อกอินผิดซ้ำๆ จาก IP เดียว → ครั้งที่ 11 ได้ 429 + `Retry-After`
2. อีเมลที่ไม่มีในระบบกับอีเมลที่มีอยู่จริง ได้ผลเหมือนกันทุกประการเมื่อถูกบล็อก
3. หมดหน้าต่างแล้วผู้ใช้จริงล็อกอินผ่านตามปกติ
4. request ที่ถูกบล็อกต้องถูกกว่าการทำ scrypt หนึ่งรอบอย่างมีนัย (วัดเป็นตัวเลข)

## สิ่งที่แก้จริง

| ไฟล์ | สิ่งที่เพิ่ม |
|---|---|
| `meeting_ai/web/ratelimit.py` (ใหม่) | ตัวนับ fixed window ในหน่วยความจำ (`hit` / `block` / `reset` / `clear`) มี lock และเพดาน `MAX_KEYS = 4096` (เกินแล้วทิ้งคีย์ที่นับได้น้อยสุดก่อน) |
| `meeting_ai/web/pgstore.py` | `rate_hit(key, limit, window)` (upsert atomic ครั้งเดียว คืนวินาทีที่ต้องรอ), `rate_reset(key)`, และ `purge_expired()` ล้างแถวหมดอายุเพิ่มอีกหนึ่งบรรทัด |
| `meeting_ai/web/schema.sql` | ตาราง `meeting_ai.rate_limits` + index `rate_limits_expires_idx` (idempotent) |
| `meeting_ai/web/server.py` | `AUTH_RATE_LIMIT/WINDOW`, `Handler.trust_proxy`, `_client_ip`, `_rate_key`, `_rate_limited`, `_rate_ok`, `_too_many`; เรียกหัว `_login`/`_signup` และล้างตัวนับเมื่อสำเร็จ |
| `meeting_ai/config.py` | `config.trust_proxy` จาก `TRUST_PROXY` |
| `api/index.py` | `trust_proxy = True` (บน Vercel มี edge คั่นเสมอ) |
| `README.md` | บอกโควตา + ต้องรัน `./mai db-init` + `TRUST_PROXY=1` เมื่ออยู่หลัง reverse proxy |

รายละเอียดที่เจอตอนรีวิวตัวเองและแก้เพิ่ม:
- **429 ถูกส่งก่อนอ่าน body** ไบต์ของ body จึงค้างในซ็อกเก็ต ถ้าปล่อย keep-alive ต่อ คำขอถัดไป
  บนสายเดิมจะถูกแยกวิเคราะห์ผิดทั้งสาย — `_too_many()` จึงส่ง `Connection: close` และตั้ง
  `self.close_connection = True` (ผลพลอยได้: คนยิงรัวต้องเปิด TCP ใหม่ทุกครั้ง)
- **ค่าใน `X-Forwarded-For` ต้องมีรูปทรงเป็น IP** (`_IP_RE`) ไม่งั้น proxy ที่ตั้งผิดทำให้แถวใน
  `rate_limits` งอกได้ไม่จำกัดตามค่าที่คนนอกกำหนด — ถ้าไม่เข้ารูปให้ตกไปใช้ `client_address`

## ผลการพิสูจน์

รันจริงบน `127.0.0.1:55480` (โหมด cloud จำลอง: patch `backend.cloud/backend.store/jobs.cloud/
jobs.store/server.store` ตามสูตรใน PROJECT-CONTEXT, `verify_password` ใช้ scrypt พารามิเตอร์
เดียวกับ `pgstore._SCRYPT` ของจริง, ตัวนับกลางจำลอง semantics เดียวกับ SQL)

| ข้อ | ผล |
|---|---|
| A ลิมิตทำงาน | ครั้งที่ 1-10 = 401, ครั้งที่ 11-12 = 429 + `Retry-After: 60`; `verify_password` ถูกเรียก **10 ครั้งจาก 12** = ไม่มี scrypt หลังถูกบล็อก |
| B ไม่รั่วว่ามีบัญชีไหม | ตอนถูกบล็อก "อีเมลจริง+รหัสถูก" / "อีเมลไม่มีจริง" / "body ว่าง" ได้ 429 + ข้อความเดียวกันทั้งหมด (0.6 ms ทั้งสามแบบ) |
| C ไม่ล็อกคนจริง | หมดหน้าต่างแล้วล็อกอินถูกต้อง → 200 + `Set-Cookie: mai_session`; ตัวนับกลางถูกล้าง (`{}`) และการยิงผิดครั้งถัดไปได้ 401 ไม่ใช่ 429 |
| D ราคา | scrypt 1 รอบ = **42.8 ms + ~16 MB**; `ratelimit.hit()` = **0.00046 ms**; HTTP 401 (ต้อง hash) = 45.7 ms; HTTP 429 (ถูกตัดก่อน) = **0.94 ms** → คำขอที่ถูกบล็อกถูกกว่า ~49 เท่า end-to-end และตัวตัดสินเองถูกกว่า scrypt ~93,000 เท่า โดยไม่จองหน่วยความจำ |
| E ปลอมหัวข้อไม่ได้ | `trust_proxy=False` + ส่ง `X-Forwarded-For: 1.2.3.4` → ยังคง 429 |
| F ทรง serverless | ล้างหน่วยความจำก่อน **ทุก** request (จำลองคนละ invocation) → ยังได้ `[401]*10 + [429,429]` = ตัวนับใน Postgres บล็อกเองได้จริง |
| G trust_proxy=True | `9.9.9.9` ถูกบล็อก, `8.8.8.8` ไม่โดนหางเลข, `"1.1.1.1, 9.9.9.9"` ยังนับเป็น 9.9.9.9 (อ่านตัวขวาสุด), `x-vercel-forwarded-for: 7.7.7.7` ชนะ `x-forwarded-for` |
| H keep-alive | 10 คำขอแรกใช้สายเดิมต่อได้ (`will_close=False`), ครั้งที่ 11 ได้ 429 + `Connection: close`, ต่อสายใหม่แล้วได้ 429 ปกติ (ไม่ใช่ 400 เพี้ยน) |

SQL พิสูจน์ด้วย fake `db.connect` ที่บันทึก `(sql, params)`: จำนวน `%s` = จำนวนพารามิเตอร์,
params = `(key, window, window)`, มีทั้ง `on conflict (key) do update`, การรีเซ็ตเมื่อ
`rate_limits.expires_at <= now()`, `make_interval(secs => %s::double precision)` (cast ชัดเจน
กันปัญหาชนิดพารามิเตอร์แบบเดียวกับ `%s::text[]` ใน `job_claim`) และ `returning hits, extract(...)`;
เคสขอบ: เหลือเวลา < 1 วิ → 1.0, `None` → 1.0, ไม่มีแถว → 0.0 (ไม่ระเบิด)

ชุดทดสอบเดิม: `PYTHONIOENCODING=utf-8 python -m unittest discover -s tests` → **64 tests OK, 1 skipped**
(เท่าเดิม) และ `python -m compileall -q meeting_ai api bot` ผ่าน

**ยังไม่ได้พิสูจน์:** SQL ไม่เคยรันกับ Postgres จริง (เครื่องนี้ไม่มี `psql` และ Docker daemon ไม่ได้
เปิดอยู่) ตรวจได้แค่รูปประโยค/พารามิเตอร์ — คนที่มี throwaway DB ควรรัน `./mai db-init` แล้วยิง
`rate_hit` สักสิบครั้งก่อนขึ้น production

  (captcha / device signal / แจ้งเตือนเจ้าของบัญชี)

# รอบรีวิวที่ 1 (2026-09-17) — ข้อค้นพบ 7 ข้อ + low

รีวิวเวอร์สองคนยืนยันว่าส่วนที่ตั้งใจให้ถูกนั้นถูก (ตัดสินก่อน `_body_json()`/`verify_password`,
ไม่รั่วว่าอีเมลมีจริง, keep-alive ไม่ desync, แม่นภายใต้ concurrency 40 คำขอขนาน) แต่มี 7 ข้อที่
ทำให้ "ลิมิตไม่ได้ลิมิตอะไรจริงในสภาพจริง" ทั้งหมดแก้แล้ว

| # | ปัญหา | สิ่งที่แก้ |
|---|---|---|
| 1 | ล็อกอินสำเร็จล้างโควตาทั้งหมด → เพดานจริงคือ "9 ครั้งต่อ 1 ความสำเร็จ" ใครมีบัญชีใบเดียวก็ยิงได้ไม่จำกัด (พิสูจน์: 45 เดา 0×429) | เพิ่ม **ถังที่สอง** `<scope>.hour:<ip>` = `AUTH_HARD_LIMIT` 60 ครั้ง/ชั่วโมง ที่ `_rate_ok()` **ไม่ล้าง** ถังแคบ 10/15 นาที ยังล้างได้ตามเดิมเพื่อกันล็อกคนจริง |
| 2 | `X-Vercel-Forwarded-For` ถูกเชื่อทุก deployment ที่ตั้ง `TRUST_PROXY=1` ทั้งที่ nginx/Cloudflare ส่งหัวข้อที่ไม่รู้จักผ่านมาตรงๆ | `Handler.forwarded_headers = ("X-Forwarded-For",)` และ override เป็นทูเพิลที่มีหัวข้อของ Vercel ใน `api/index.py` เท่านั้น |
| 3 | `_IP_RE` ไม่ใช่ตัวแปลง IP (ผ่านทั้ง `....`, `999.999.999.999`, `127.0.0.1:8080`) และ IPv6 นับที่ /128 | ตัดทิ้ง ใช้ `_ip_key()` บน `ipaddress` ของ stdlib: ตัดพอร์ต (`host:port`, `[v6]:port`), ปฏิเสธขยะ (ตกไปใช้ `client_address`), ยุบ `::ffff:` และนับ IPv6 เป็น **/64** |
| 4 | `_prune` ทิ้งคีย์ที่เพิ่งนับในการเรียกเดียวกัน → พอคีย์เต็มเพดาน ชั้นหน่วยความจำ "หยุดนับ" ทั้งชั้น | ตัดแต่ง **ก่อน** ใส่คีย์ใหม่, ห้ามทิ้ง `keep`, ไล่ทิ้งรายการที่ยังไม่ถูกบล็อกโดยเรียงตามหมดอายุเร็วสุด และมีเพดานแข็ง `HARD_MAX_KEYS` |
| 5 | fail-open เงียบสนิทเมื่อยังไม่ได้ `db-init` | `_warn_rate_db()` เตือน stderr **ครั้งเดียว** (flag ระดับโมดูล) พร้อมบอกให้รัน `mai db-init` |
| 6 | คนนอกยิงขยะ 11 ครั้งล็อกทุกคนหลัง NAT เดียวกันได้ และรหัสที่ถูกต้องก็ถูกตัดก่อนถึง `verify_password` จึงล้างถังไม่ได้ | คำขอที่ถือ `mai_session` ที่ยังใช้ได้ **ข้ามถังแคบ** (ไม่ข้ามถังแข็ง) — คนที่ล็อกอินอยู่แล้วไม่โดนลูกหลง |
| 7 | `purge_expired()` ไม่มีใครเรียก แถวจึงค้างตลอดอายุระบบ | `rate_hit()` พ่วงงานเก็บกวาดแบบฉวยโอกาส (`RATE_PURGE_CHANCE = 0.01`, ลบแถวที่หมดอายุเกิน 1 ชั่วโมง, ล้มเหลวแล้วเงียบ) |
| low | 429 ที่ตอบคำขอ body ใหญ่ทำให้ client เจอ TCP reset | `_drain_body()` อ่านทิ้งไม่เกิน 64 KB (timeout 2 วิ) ก่อนตอบแล้วปิดสาย — ป้องกัน AttributeError บน Vercel ที่ `self.connection` ไม่ใช่ซ็อกเก็ตจริง |
| low | คอมเมนต์ที่ `_signup` อ้าง scrypt ผิด | เขียนใหม่: คนไม่มีรหัสเชิญถูกตีกลับก่อนถึง `set_password` ภัยจริงคือเดารหัสเชิญ + ยิง DB ฟรี |

**คืนของนอกสโคปที่เผลอติดมา:** `sed` ของรอบแรกเติม `::double precision` ให้ `make_interval`
ทุกที่ในไฟล์ รวมถึง `job_request_stop` (`pgstore.py:690`) และ `worker_capabilities` (`:816`)
ซึ่งไม่เกี่ยวกับตั๋วนี้และทดสอบกับ Postgres จริงที่นี่ไม่ได้ — **revert แล้ว** เหลือ cast เฉพาะสอง
แห่งใน `rate_hit` (มีเทสต์ในสคริปต์พิสูจน์ SQL ว่าไฟล์ทั้งไฟล์มี `::double precision` เพียง 2 ครั้ง)

## ผลการพิสูจน์รอบที่ 2 (127.0.0.1:55482, cloud จำลอง)

| ข้อ | ผล |
|---|---|
| 1 | วน "เดา 9 + ล็อกอินตัวเอง 1" 10 รอบ = 100 คำขอ → `verify_password` ถูกเรียก **60 ครั้งพอดี** (= เพดานรายชั่วโมง) 429 เกิด 36 ครั้ง; ก่อนแก้ 45 เดาแรกได้ 0×429 |
| 2 | `trust_proxy=True` + สลับ `X-Vercel-Forwarded-For` ทุกคำขอ 40 ครั้ง → 401×10 / 429×30 และสร้างคีย์แค่ **2** คีย์ (ก่อนแก้: 40×401, 40 แถว) |
| 3 | `_ip_key`: `127.0.0.1:8080`→`127.0.0.1`, `[2001:db8::1]:443`→`2001:db8::/64`, `::ffff:1.2.3.4`→`1.2.3.4`, `....`/`:::`/`abc`/`999.999.999.999`→`""` (ตกไปใช้ที่อยู่ TCP จริง) · 50 คำขอจาก /64 เดียวกัน → 401×10 / 429×40 · IPv4 ต่อพอร์ตต่างกัน 12 ครั้ง → 429×2 |
| 4 | เติมจนครบ `MAX_KEYS` แล้วยิงคีย์เหยื่อ 30 ครั้ง → บล็อกตั้งแต่ครั้งที่ 11 และคีย์เหยื่อยังอยู่ในตาราง; ยิงคีย์ใหม่อีก 8192 คีย์ → คีย์ที่ถูกบล็อกยังอยู่ ขนาดไม่เกินเพดานแข็ง |
| 5 | ตารางหาย + จำลอง serverless 12 คำขอ → ยังตอบ 401 (fail-open ตามตั้งใจ) แต่มีบรรทัดเตือน stderr **1 บรรทัด** ที่บอกให้รัน `db-init` |
| 6 | ถังแคบเต็ม: ไม่มีคุกกี้ → 429, คุกกี้ปลอม → 429, `mai_session` ที่ใช้ได้ → **200**; แต่เมื่อถังแข็งเต็ม session ก็ยัง → 429 (คุกกี้ไม่กลายเป็นทางลัด) |
| 7 | fake `db.connect`: `RATE_PURGE_CHANCE=0` → 1 statement, `=1` → มี `delete ... where expires_at < now() - interval '1 hour'` ต่อท้าย |
| low | ยิง body 256 KB ตอนถูกบล็อก 3 ครั้ง → อ่านคำตอบ 429 ได้ครบ 3/3 (ก่อนแก้ 2 ใน 3 ครั้งเป็น connection reset) |

ข้อพิสูจน์รอบแรก (A-H) รันซ้ำแล้วยังผ่านทั้งหมด ยกเว้นสองข้อที่ **เปลี่ยนตามเจตนาใหม่**:
