# BUG-012 — Invite redemption TOCTOU (สมัครพร้อมกันด้วยรหัสเชิญเดียวได้หลายบัญชี)

| | |
|---|---|
| Backlog | P1 #12 (พ่วงแก้ race `first_run` ที่ยังไม่อยู่ใน backlog) |
| Owner | backend-dev |
| Severity | High — access-control bypass ของระบบที่ตั้งใจให้สมัครได้เฉพาะคนที่มีรหัสเชิญ |
| Affects | โหมด cloud เท่านั้น (`POST /api/auth/signup`); โหมดไฟล์ `_auth_api` ตอบ 501 |
| Status | fixed 2026-09-17 — branch `fix/backlog-12-invite-toctou` (ตรวจซ้ำ + พิสูจน์ใหม่ 2026-09-17) |

## อาการ

`_signup()` ([meeting_ai/web/server.py](../../meeting_ai/web/server.py)) ตัดสินใจสองเรื่องด้วยการ **อ่านก่อนแล้วค่อยเขียน** โดยไม่มีอะไรกั้นระหว่างกลาง

1. **รหัสเชิญ** — `store.invite_email(invite)` เป็น `select ... where used_by is null` ธรรมดา
   ([pgstore.py:202](../../meeting_ai/web/pgstore.py)) แล้วจึงสร้างผู้ใช้ + ตั้งรหัสผ่าน แล้วจึงเรียก
   `store.redeem_invite(invite, user["id"])` ซึ่งเป็น `update ... where used_by is null` แบบ atomic จริง
   ([pgstore.py:189](../../meeting_ai/web/pgstore.py)) — **แต่ค่า boolean ที่คืนมาถูกทิ้ง**
   ยิงสมัครพร้อมกัน N ครั้งด้วยรหัสเชิญเดียว (คนละอีเมล): ทุก request ผ่าน select, สร้างบัญชีครบ N ใบ,
   `redeem_invite` สำเร็จแค่ใบเดียว และไม่มีใครดูผลลัพธ์ → **1 รหัสเชิญ = N บัญชี**
2. **ผู้ใช้คนแรกเป็นแอดมิน** — `first_run = store.count_users() == 0` มีรูปแบบเดียวกันเป๊ะ
   สมัครพร้อมกันสองคนตอนระบบยังว่าง ทั้งคู่เห็น 0 → **ได้ `is_admin = true` ทั้งคู่**
   (แอดมินออกรหัสเชิญได้ = ขยายสิทธิ์ต่อได้เรื่อยๆ)

ทั้งสองจุดไม่ใช่แค่ความไม่เรียบร้อย แต่เป็นการข้ามการควบคุมสิทธิ์: ระบบนี้ตั้งใจให้สมัครได้เฉพาะคนที่ได้รับเชิญ

## เงื่อนไขที่ต้องทำให้ได้

- จุดตัดสินต้องเป็น **statement เดียว** ที่เอาเงื่อนไขไว้ใน `where` (สไตล์เดียวกับ `redeem_invite` เดิม)
  ห้ามเพิ่มตาราง lock, ห้าม retry loop, ห้ามถือ transaction ยาวคร่อม scrypt
  (`db.connect()` เป็น `autocommit=True` และพูลมีแค่ `max_size=4` — ล็อกแถวคร่อมการ hash รหัสผ่าน
  ~100 ms จะกินคอนเนกชันของทั้ง instance)
- เชิญไม่สำเร็จต้องตอบ **409** พร้อมข้อความไทย และ **ห้ามบอก** ว่ารหัสนั้นไม่มีจริง / หมดอายุ / ถูกใช้ไปแล้ว
- โหมดไฟล์ไม่ต้องมีฟังก์ชันคู่แฝดใน `store.py` — ตรวจแล้ว: `_auth_api()` ตอบ 501 ตั้งแต่บรรทัดแรกเมื่อ
  `backend.auth_required()` เป็น False และ `store.py` ไม่มี `count_users/invite_email/redeem_invite` อยู่แล้ว
  จึงไม่มี call site ไหนของฟังก์ชันชุดนี้ที่หลุดออกนอกโหมด cloud

## ทางเลือกที่ชั่งแล้ว

| แนวทาง | ผลถ้าขั้นถัดจากจุด atomic ล้ม | สรุป |
|---|---|---|
| A. **จองรหัสเชิญก่อนสร้างผู้ใช้** แล้วค่อยผูก `used_by` ทีหลัง | รหัสเชิญถูกเผา (claimed แต่ไม่มีเจ้าของ) ต้องออกใบใหม่ | **เลือกอันนี้** — ปิดช่องได้จริง, statement เดียว, ไม่มีบัญชีเถื่อนเกิดขึ้นเลยเมื่อแพ้ race |
| B. ทำทั้งชุดใน transaction เดียว (`db.transaction()`) | ไม่มีสถานะค้าง | ต้องถือล็อกแถว invites คร่อม `ensure_user` + scrypt และย้ายตรรกะสมัครลงไปอยู่ใน pgstore ทั้งก้อน; พูล 4 คอนเนกชันตันง่าย |
| C. คงลำดับเดิม แต่เช็กค่าที่ `redeem_invite` คืน แล้วลบผู้ใช้ทิ้งเมื่อแพ้ | เหลือผู้ใช้กำพร้าที่ตั้งรหัสผ่านไปแล้ว (ล็อกอินได้) ถ้าการลบล้ม | อันตรายที่สุด: `ensure_user` เป็น upsert on conflict (email) การลบอาจไปโดนผู้ใช้เดิมที่มีอยู่ก่อน |

## การแก้ (แนวทาง A ทั้งสองจุด — "จองก่อน ค่อยสร้าง")

`meeting_ai/web/pgstore.py`

- `claim_invite(code, email) -> bool` — จองรหัสเชิญด้วย statement เดียว
  `update meeting_ai.invites set used_at = now() where code_hash = %s and used_by is null and used_at is null and (expires_at is null or expires_at > now()) and (invites.email is null or invites.email = %s) returning code_hash`
  เงื่อนไขครบทั้ง มีจริง / ยังไม่ถูกจอง / ยังไม่หมดอายุ / ผูกอีเมลตรง อยู่ใน `where` ทั้งหมด
  แถว invites ถูกล็อกโดย Postgres เอง → มีผู้ชนะได้แค่รายเดียว
- `attach_invite(code, user_id) -> bool` — ผูกเจ้าของหลังสร้างผู้ใช้สำเร็จ
  `update ... set used_by = %s where code_hash = %s and used_by is null and used_at is not null`
  (แทนที่ `redeem_invite()` เดิม ซึ่งถูกลบทิ้ง — เหลือไว้จะถูกเรียกผิดวิธีซ้ำรอยเดิม)
- `claim_first_admin(email) -> bool` — จองสิทธิ์ "ผู้ใช้คนแรกของระบบ" ด้วย statement เดียว
  ใช้ unique key ของตาราง `settings` เป็นตัวตัดสิน (คีย์ `signup_bootstrap`, value = อีเมลที่จอง)
  `insert into meeting_ai.settings (key, value, updated_at) values ('signup_bootstrap', %s::jsonb, now()) on conflict (key) do update set value = excluded.value, updated_at = now() where settings.value = excluded.value returning key`
  - คนแรกที่ยิงถึง insert สำเร็จ → `returning` มีแถว → เป็นแอดมิน
  - คนที่สองชนกันที่ primary key → `do update ... where settings.value = excluded.value` เป็นเท็จ
    (อีเมลคนละตัว) → ไม่มีแถวคืน → ไม่ได้เป็นแอดมินและ **ไม่ถูกสร้างบัญชี**
  - อีเมลเดิมยิงซ้ำ (retry หลังล้มกลางทาง) → เงื่อนไขเป็นจริง → ชนะอีกครั้ง ระบบไม่ตาย
  - หมายเหตุ: ใช้ `insert ... on conflict` แทนการอ่าน `count(*)` เพราะภายใต้ READ COMMITTED
    `not exists (select 1 from users)` ของสอง transaction ที่ insert คนละแถวไม่ชนกัน — ทั้งคู่ผ่าน
- `invite_email()` เพิ่ม `and used_at is null` ให้ predicate ตรงกับ `claim_invite`
  (ยังเป็นแค่ pre-check เพื่อเลือกข้อความเท่านั้น — ไม่ใช่การตัดสินใจด้านสิทธิ์อีกต่อไป)

`meeting_ai/web/server.py` (`_signup`)

ลำดับใหม่: ตรวจรูปแบบอีเมล/รหัสผ่าน → pre-check เฉพาะที่ให้ข้อความดีกว่า (ไม่กรอกรหัสเชิญเลย → 403 ข้อความเดิม,
รหัสผูกกับอีเมลอื่น → 403 ข้อความเดิม) → `has_password` (409 เดิม, **เฉพาะเมื่อ `first_run or invite_ok`**) → **จุด atomic**:
`claim_first_admin(email)` หรือ `claim_invite(invite, email)` → `ensure_user` → `set_password` → `attach_invite`
ไม่ผ่านจุด atomic = ตอบ 409 ทันที โดยยังไม่มีการสร้างอะไรเลย

**สำคัญ — pre-check ตัวเดิมถูกถอดออกจากการตัดสิน**: ของเดิม `invite_email()` คืน "ใช้ไม่ได้" แล้ว
return 403 ทันที ทำให้กรณี "รหัสถูกใช้ไปแล้ว" แบบยิงทีละครั้งได้ 403 แต่แบบยิงพร้อมกันได้ 409 — คนละรหัส
สำหรับความล้มเหลวเรื่องเดียวกัน (เจอตอนรันชุดพิสูจน์รอบแรก) ตอนนี้รหัสเชิญที่ไม่มีจริง/หมดอายุ/ถูกใช้แล้ว
ตกไปที่ `claim_invite` เสมอ และได้ **409 ข้อความเดียวกันทุกกรณี** ไม่ว่าจะแข่งกันหรือไม่

**สำคัญ 2 — กัน oracle เดาอีเมล (พบตอนรีวิวรอบสอง 2026-09-17, แก้แล้ว)**: 403 ตัวเดิมไม่ได้ทำหน้าที่แค่
ตัดสินสิทธิ์ แต่ยัง "บัง" บรรทัด `has_password` ที่อยู่ถัดไปด้วย (คอมเมนต์เดิมเขียนไว้ตรงๆ ว่า *ไม่บอกว่า
อีเมลนี้มีบัญชีอยู่แล้วหรือไม่ กัน enumerate*) พอย้ายการตัดสินไปที่ `claim_*` แล้วปล่อย `has_password`
ให้ทุกคนเข้าถึง ผลคือใครก็ได้ยิงรหัสเชิญมั่วๆ + อีเมลเป้าหมาย แล้วอ่านความต่างของข้อความ 409 สองแบบ
เพื่อรู้ว่าอีเมลนั้นมีบัญชีในระบบหรือไม่ — เป็น **ช่องใหม่ที่การแก้ TOCTOU สร้างขึ้นเอง**
ปิดด้วยการคุม `has_password` ไว้หลัง `first_run or invite_ok` ผลที่ได้:
- ไม่มีรหัสเชิญที่ใช้ได้ → ได้ข้อความเดียวเสมอ ไม่ว่าอีเมลนั้นจะมีบัญชีหรือไม่ (ระดับการเปิดเผยเท่าของเดิม)
- ถือรหัสเชิญที่ใช้ได้จริงแล้วกรอกอีเมลซ้ำ → ยังได้ 409 "มีบัญชีอยู่แล้ว" ตามเดิม **และรหัสเชิญไม่ถูกเผา**
  (เพราะเช็กก่อนถึงจุด atomic) — เหตุผลที่ไม่ย้าย `has_password` ไปไว้หลัง `claim_invite`
- ไม่มีช่องเขียนทับรหัสผ่านบัญชีเดิม: `invite_ok = False` แล้ว `claim_invite` สำเร็จไม่ได้
  เพราะสถานะรหัสเชิญเดินทางเดียว (ว่าง → ถูกจอง) ย้อนกลับไม่ได้ และ `code_hash` เป็น primary key

ข้อความ 409 (ไทย, ไม่บอกสาเหตุย่อย):
- รหัสเชิญ: `"รหัสเชิญนี้ใช้ไม่ได้แล้ว (ขอรหัสใหม่จากแอดมินของทีม) — ถ้ามีบัญชีอยู่แล้วให้เข้าสู่ระบบแทน"`
- ผู้ใช้คนแรก: `"ระบบนี้มีผู้ใช้คนแรกไปแล้ว — ต้องใช้รหัสเชิญจากแอดมินจึงจะสมัครได้"`
  (ไม่ถือว่ารั่ว: `GET /api/auth/me` เปิดเผย `first_run` อยู่แล้ว)

## ถ้าขั้นถัดจากจุด atomic ล้ม (ตอบตามที่โจทย์ถาม)

- **จองรหัสเชิญสำเร็จ แต่ `ensure_user`/`set_password` ล้ม** → รหัสเชิญนั้นถูกเผา (`used_at` ถูกตั้ง, `used_by` ยัง null)
  ผู้ใช้ไม่ถูกสร้าง, ไม่มีบัญชีค้าง, คนอื่นเอารหัสนั้นไปใช้ต่อไม่ได้ (ทางที่ปลอดภัย) — ต้องขอรหัสใหม่จากแอดมิน
  **ไม่ใส่ compensating release ในโค้ด** โดยตั้งใจ: ความล้มเหลวที่เป็นไปได้จริงในจุดนี้คือ DB ล่ม
  ซึ่งคำสั่งคืนสถานะก็จะล้มตามอยู่ดี และการ "ปลดล็อก" เองเป็นพื้นผิว race เพิ่มอีกจุด
  แอดมินกู้เองได้ด้วยคำสั่งเดียว (ดูหัวข้อ Runbook ข้างล่าง)
- **จองสำเร็จ สร้างผู้ใช้สำเร็จ แต่ `attach_invite` ล้ม** → บัญชีใช้งานได้ตามปกติ, รหัสเชิญยังนับว่าถูกใช้แล้ว
  (ผลลัพธ์ที่ถูกต้อง) เสียแค่ audit trail ว่าใครใช้ — ยอมรับได้
- **จองสิทธิ์แอดมินคนแรกสำเร็จ แต่สร้างผู้ใช้ล้ม** → คีย์ `signup_bootstrap` ค้างไว้ที่อีเมลนั้น
  คนเดิมสมัครซ้ำได้ทันที (statement ออกแบบให้ idempotent ต่ออีเมลเดิม) ระบบไม่ตาย
  ถ้าต้องเปลี่ยนไปใช้อีเมลอื่น แอดมิน/เจ้าของต้องลบคีย์ทิ้ง (ดู Runbook)

## Runbook (เจ้าของระบบ)

- **migration: ไม่มี** — ใช้คอลัมน์ `invites.used_at` และตาราง `settings` ที่มีอยู่แล้ว
  `web/schema.sql` ไม่ถูกแก้ ไม่ต้องรัน `./mai db-init` เพิ่ม ไม่ต้อง backfill
  (ระบบที่มีผู้ใช้อยู่แล้วจะไม่แตะคีย์ `signup_bootstrap` เลย เพราะ `count_users() > 0`)
- ปลดรหัสเชิญที่ถูกจองแต่สมัครไม่สำเร็จ:
  `update meeting_ai.invites set used_at = null where used_by is null and used_at < now() - interval '1 hour';`
- เริ่มขั้นตอนตั้งแอดมินคนแรกใหม่ (เช่น จองด้วยอีเมลผิด):
  `delete from meeting_ai.settings where key = 'signup_bootstrap';`

## ข้อพิสูจน์ที่ต้องมี (concurrency ไม่ใช่ sequence)

1. N เธรดยิง `POST /api/auth/signup` พร้อมกันด้วยรหัสเชิญเดียว คนละอีเมล → สำเร็จ 1, ที่เหลือ 409,
   จำนวนผู้ใช้ที่ถูกสร้าง = 1
2. N เธรดยิงสมัครพร้อมกันตอนระบบยังว่าง → เป็นแอดมิน 1 คน, ที่เหลือ 409, ผู้ใช้ทั้งระบบ = 1
3. เคสลำดับเดิมต้องไม่พัง: สมัครด้วยรหัสเชิญที่ใช้ได้ → 200; ใช้ซ้ำ → 409; รหัสผูกอีเมลอื่น → 403;
   ไม่มีรหัส → 403; อีเมลซ้ำ → 409

*(regression test เป็นงานของ test-engineer — ticket นี้พิสูจน์ด้วยสคริปต์ชั่วคราวใน scratchpad)*

## ผลการพิสูจน์ (2026-09-17, 127.0.0.1:55500)

ยิง HTTP จริงเข้า `server.Handler` ที่รันบน `ThreadingHTTPServer` จาก 8 เธรดพร้อมกัน (`threading.Barrier`)
store ปลอมบังคับ atomicity ต่อ statement ด้วย `threading.Lock` และหน่วงใน `has_password`/`ensure_user`
เพื่อถ่างหน้าต่าง TOCTOU ให้กว้างที่สุด

| เคส | ก่อนแก้ (negative control) | หลังแก้ |
|---|---|---|
| 8 signup พร้อมกัน 1 รหัสเชิญ | `200 × 7` + `403 × 1`, **สร้างบัญชี 7 ใบจากรหัสเดียว** | `200 × 1` + `409 × 7`, บัญชีใหม่ **1 ใบ**, `used_by` ผูกกับคนที่ชนะ |
| 8 signup พร้อมกันตอนระบบว่าง | `200 × 6` + `403 × 2`, **แอดมิน 6 คน / ผู้ใช้ 6 คน** | `200 × 1` + `409 × 4` + `403 × 3` (มาช้าและไม่มีรหัสเชิญ), ผู้ใช้ **1 คน** แอดมิน **1 คน** |

(ตัวเลขข้างบนคือการรันซ้ำแบบอิสระเมื่อ 2026-09-17; จำนวน `409`/`403` ของฝั่งผู้แพ้แกว่งได้ตามจังหวะเธรด
เพราะคนที่มาถึง `count_users()` หลังผู้ชนะสร้างบัญชีเสร็จจะตกเส้นทาง "ไม่มีรหัสเชิญ" → 403
สิ่งที่คงที่ทุกรอบคือ **ผู้ชนะ 1 ราย / บัญชี 1 ใบ / แอดมิน 1 คน**)

พยานว่าหน้าต่าง race ถูกเปิดจริง (สคริปต์ assert เอง ไม่ใช่แค่ดูตาเปล่า): นับ 6 เธรดที่ผ่าน pre-check
ตอนรหัสเชิญยังว่าง และ 5 เธรดที่เห็น `count_users() == 0` พร้อมกัน — ถ้าเธรดไม่ทับกันเลยตัวเลขนี้จะเป็น 1
และการทดสอบจะพิสูจน์อะไรไม่ได้ (เทสต์แบบยิงทีละครั้งผ่านแม้บั๊กยังอยู่)
เคสลำดับเดิม 18 ข้อผ่านครบ (ดูหัวข้อ "ข้อพิสูจน์ที่ต้องมี" ข้อ 3) ข้อความ 409 ของ
"ไม่มีจริง / หมดอายุ / ถูกใช้แล้ว" เป็นสตริงเดียวกันเป๊ะ และไม่มีคำว่า ไม่มี/หมดอายุ/ถูกใช้ อยู่ในข้อความ
`claim_first_admin` ยัง idempotent ต่ออีเมลเดิม (จองซ้ำได้) และปฏิเสธอีเมลอื่น

ชุดพิสูจน์ oracle (เพิ่มรอบสอง): ยิงรหัสเชิญมั่ว + อีเมลที่ "มีบัญชี" กับอีเมลที่ "ไม่มีบัญชี" ต้องได้
สตริงเดียวกันเป๊ะ และต้องเท่ากับข้อความของรหัสเชิญใช้ไม่ได้ปกติ, ยิงแบบไม่กรอกรหัสเชิญทั้งสองอีเมล
ต้องได้สตริงเดียวกัน, และรหัสเชิญที่ยังดีต้อง **ไม่ถูกเผา** เมื่อเจอ 409 อีเมลซ้ำ — ผ่านทั้งหมด
(ก่อนแก้ข้อนี้ สองเคสแรก **FAIL** จริง: ได้ `"อีเมลนี้มีบัญชีอยู่แล้ว…"` กับ `"รหัสเชิญนี้ใช้ไม่ได้แล้ว…"`)

นอกจากนี้ยังบันทึก SQL จริงที่ pgstore ส่งออก (fake `db.connect` ที่เก็บ `(sql, params)`) แล้วตรวจว่า
แต่ละฟังก์ชันยิง **statement เดียว**, จำนวน `%s` เท่ากับจำนวนพารามิเตอร์, ไม่มีการต่อสตริงค่าเข้าไปใน SQL,
มี `returning` ทุกจุดตัดสิน, `where` ของ `claim_invite` ครบทุกเงื่อนไข, `claim_first_admin` ชนกันที่
`on conflict (key)` พร้อม `where settings.value = excluded.value` และ `redeem_invite` เดิมถูกถอดออกจริง
(`hasattr(pgstore, "redeem_invite") is False` — ไม่มีทางเรียกแบบเก่าได้อีก)

## ข้อจำกัดของการพิสูจน์บนเครื่องนี้

เครื่องพัฒนาไม่มี Postgres (ไม่มี `psql`, Docker daemon ไม่ทำงาน) — สิ่งที่พิสูจน์ได้คือ
**ตรรกะชั้น server.py** ว่าใช้ผลของ claim อย่างถูกต้องภายใต้การยิงพร้อมกันจริง (จำลอง store ที่บังคับ
atomicity ด้วย `threading.Lock` ตามความหมายของแต่ละ statement) และ **ข้อความ SQL + จำนวนพารามิเตอร์**
(fake `db.connect` ที่บันทึก `(sql, params)`) ส่วนที่ยัง **ไม่ได้ verify กับ Postgres จริง** คือพฤติกรรม
การล็อกแถวของ `update ... where` และ `insert ... on conflict do update ... where` ภายใต้ READ COMMITTED
(อ้างอิงพฤติกรรมมาตรฐานของ Postgres) — ควรรันข้อพิสูจน์ข้อ 1-2 อีกครั้งกับ DB ทิ้งขว้างก่อนขึ้น production

## สิ่งที่ฝั่ง client / ผู้ทดสอบต้องรู้

- `POST /api/auth/signup` ด้วยรหัสเชิญที่ไม่มีจริง/หมดอายุ/ถูกใช้แล้ว เปลี่ยนจาก **403 → 409**
  (403 เหลือไว้สองกรณี: ไม่กรอกรหัสเชิญเลย, และรหัสถูกผูกกับอีเมลอื่น)
  `app.js` แสดงข้อความจาก `data.error` ของทุกสถานะที่ไม่ใช่ 2xx อยู่แล้ว (`api()` บรรทัด 74)
  จึงไม่ต้องแก้ฝั่งหน้าเว็บ — แต่เทสต์/สคริปต์ที่ hardcode 403 ไว้ต้องอัปเดต
- รหัสเชิญที่ใช้ไม่ได้ + อีเมลที่มีบัญชีอยู่แล้ว ตอบ `"รหัสเชิญนี้ใช้ไม่ได้แล้ว…"` (ไม่ใช่ `"อีเมลนี้มีบัญชีอยู่แล้ว…"`)
  ตั้งใจให้เป็นแบบนี้เพื่อกันเดาอีเมล ข้อความนั้นมีท้ายประโยคว่า "ถ้ามีบัญชีอยู่แล้วให้เข้าสู่ระบบแทน" อยู่แล้ว
- ไม่มีฟิลด์ใน response เปลี่ยน (`{"user": …}` เหมือนเดิม)

## นอกขอบเขต (ส่งต่อ bug-triager)

- ยังไม่มี rate limit ที่ `POST /api/auth/signup` / `login` (BACKLOG #10) — race นี้ปิดแล้ว แต่การเดารหัสเชิญยังยิงรัวได้
- ข้อความ 403 `"รหัสเชิญนี้ออกให้อีเมล … เท่านั้น"` เปิดเผยอีเมลที่ผูกไว้ให้ใครก็ตามที่ถือรหัสเชิญ (พฤติกรรมเดิม ไม่แก้ในตั๋วนี้)
- `user["is_admin"] = first_run or user.get("is_admin", False)` ใน `_signup` เชื่อ `first_run` แทนค่าจริงในฐาน
  (ปัจจุบันไม่มีทางเกิดเพราะ first_run แปลว่าไม่มีผู้ใช้เลย) — เป็นความเปราะบางที่ควรแก้ตอนมีฟีเจอร์ตั้งแอดมินเพิ่ม
