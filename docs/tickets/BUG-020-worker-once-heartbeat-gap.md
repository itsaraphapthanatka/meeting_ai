- **Severity:** P1 (BACKLOG #20) — งานที่ทำไปแล้วเกือบเสร็จถูกโยนกลับเข้าคิว/ตีเป็น error, เวลา GPU + ค่า LLM เสียเปล่า, งานบอทกู้ไม่ได้
- **Owner:** backend-dev (verify: test-engineer)
- **Status:** **fixed (uncommitted)** 2026-09-17
- **ไฟล์:** [meeting_ai/worker.py](../../meeting_ai/worker.py) — `run()` เฉพาะ `beat()` กับลูปรองานตอนจะออก
- **BACKLOG ชี้ไปที่** `worker.py:311` (`while not stopping["flag"]`) และ `worker.py:404` (`for _ in range(600)`) — ตรงทั้งสองจุด (ตรวจกับ HEAD `1d225e6`)

## เกิดอะไรขึ้น

โหมด `--once` ตั้งธง `stopping["flag"] = True` **ทันทีที่คว้างานมาได้** คือก่อนงานจะเริ่มทำด้วยซ้ำ
([worker.py:399-401](../../meeting_ai/worker.py#L399) ก่อนแก้) แล้วธงใบเดียวกันนี้ถูกใช้สองความหมายพร้อมกัน:

```python
    def beat() -> None:
        while not stopping["flag"]:          # <- 311 ความหมายที่ 1: "เลิกเต้น"
            ...
            client.heartbeat(worker_name, "busy" if busy else "idle", first, gpu, refresh_caps())
            for _ in range(int(HEARTBEAT_SEC * 2)):
                if stopping["flag"]:
                    return
                time.sleep(0.5)
    ...
        if once:
            stopping["flag"] = True          # ความหมายที่ 2: "เลิกคว้างานใหม่"
            break

    for _ in range(600):                     # <- 404 รองานค้างได้แค่ 10 นาที
        with active_lock:
            if not active:
                break
        time.sleep(1)
```

ผลสองชั้น:

1. **heartbeat เงียบทั้งช่วงที่งานกำลังทำ** — เธรด `beat()` ออกทันทีที่ธงถูกตั้ง ตั้งแต่วินาทีที่ claim สำเร็จ
2. **โปรเซสออกหลังรอแค่ 600 วินาที** — เธรดงานเป็น `daemon=True` จึงถูกฆ่ากลางคันเมื่อล่าม Python ปิดตัว
   งานค้างสถานะ `running` โดยไม่มีใครรายงานต่อ

เส้นทางเดียวกันเกิดกับ **Ctrl+C** ด้วย (`on_signal` ตั้งธงใบเดียวกันระหว่างงานยังเดินอยู่) ไม่ใช่แค่ `--once`

## ฝั่งเซิร์ฟเวอร์ตัดสินว่า worker ตายเมื่อไร (ตรวจจริง ไม่ใช่เดา)

`stale_after` มีสองที่จริงตามที่ PROJECT-CONTEXT ระบุ แต่ **ใช้งานจริงแค่ตัวเดียว**:

| ที่ | ค่า | ใครใช้ |
|---|---|---|
| [pgstore.py:858](../../meeting_ai/web/pgstore.py#L858) `WORKER_STALE_SECONDS = 75` | 75 | `workers_list()` (คำนวณ `alive`/`status='gone'` และกลบ `job_id`/`job_title`) และ `worker_capabilities()` (`where last_seen > now() - 75s`) |
| [server.py:1238](../../meeting_ai/web/server.py#L1238) `self._json({"ok": True, "stale_after": 75})` | 75 | ตอบกลับไปกับ heartbeat เฉย ๆ — `worker.Client.heartbeat()` **ไม่ได้อ่านค่านี้เลย** (เป็นเลขตายตัวซ้ำซ้อน = BACKLOG #33) |

**สำคัญ: `jobs_reap()` ไม่ได้ดู heartbeat** [pgstore.jobs_reap()](../../meeting_ai/web/pgstore.py#L964) ตัดสินจาก
`coalesce(updated_at, claimed_at) < now() - 30 min` ของ **ตาราง jobs** ซึ่งขยับทุกครั้งที่ worker POST `progress`
และมันถูกเรียกจาก [jobs.claim()](../../meeting_ai/web/jobs.py#L441) เท่านั้น (คือ "ตอนมี worker ตัวใดตัวหนึ่งมาขอคิว" ไม่ใช่ cron)
งาน `kind <> 'bot'` → กลับเป็น `queued`, งาน `kind = 'bot'` → `error` ("เครื่องประมวลผลหลุดกลางทาง… ต้องส่งบอทใหม่เอง")

ดังนั้นสายเหตุ-ผลที่แท้จริงคือ **ชั้นที่ 2 (โปรเซสออกก่อนงานจบ)** เป็นตัวที่ทำให้ `updated_at` หยุดนิ่งจนโดน reap
ส่วน **ชั้นที่ 1 (heartbeat เงียบ)** ทำให้เซิร์ฟเวอร์เห็นเครื่องเป็น `gone` ระหว่างงานยังเดิน — คนละกลไก แต่มาจากธงใบเดียวกัน
และมีของแถมอีกใบ: [pgstore.job_request_stop()](../../meeting_ai/web/pgstore.py#L749) ถือว่างานที่ `updated_at` เก่ากว่า
`STOP_ORPHAN_SECONDS = 120` คือ "งานที่ไม่มีใครถืออยู่" แล้ว **ยกเลิกทิ้งทันทีเมื่อผู้ใช้กดปุ่มหยุด** — หน้าต่างนี้แค่ 2 นาที

## ผลกระทบที่ผู้ใช้เห็น

- งาน `process`/`summarize`/`translate` ที่ทำไปเกือบเสร็จ ถูกคืนคิวแล้วทำใหม่ทั้งหมด (จ่ายค่า LLM + เวลา GPU ซ้ำ; ครบ `MAX_ATTEMPTS` แล้วจบเป็น error)
- งาน `bot` หายถาวร — reaper ตีเป็น error โดยเจตนา เพราะย้อนกลับไปอัดประชุมเดิมไม่ได้
- ระหว่างงานยังเดิน หน้าเว็บขึ้น "เงียบไป …"/`gone` และ `worker_capabilities()` คืน `workers: 0`
  → `_diarize_state`/`_bot_state` ตอบ "ยังไม่มีเครื่องประมวลผลออนไลน์ — เปิด worker ก่อน" ทั้งที่มีเครื่องทำงานอยู่
- ใครโดนบ้าง (ตรวจแล้ว): `mai worker --once` คือโหมดที่ README บรรทัด 316 แนะนำไว้ว่า "ทดสอบ: ทำงานเดียวแล้วออก" และเป็นสูตรของ
  PROJECT-CONTEXT/e2e-tester — ส่วนบริการที่รันยาว (`meeting-ai-worker.service`, `worker-service.ps1`) **ไม่ได้** ใช้ `--once`
  แต่เจอบั๊กเดียวกันทุกครั้งที่กด **Ctrl+C** ระหว่างมีงานเดินอยู่ เพราะ `on_signal` ตั้งธงใบเดียวกัน — และข้อความที่มันพิมพ์คือ
  "จะหยุดหลังงานปัจจุบันจบ" เพดาน 600 วิ จึงทำให้โค้ดโกหกข้อความของตัวเองทันทีที่งานยาวกว่า 10 นาที

## หลักฐานว่าเกิดจริง (รันจริง 2026-09-17)

สคริปต์รีโปร: โปรเซส worker **ของจริง** (`worker.run(once=True)`) คุยกับเซิร์ฟเวอร์ปลอมบน `127.0.0.1:55440`
ที่เลียนกฎของจริงสองข้อ — worker ตายเมื่อ `now - last_seen > STALE` และ `jobs_reap`:
`running and kind<>'bot' and updated_at < now - REAP → queued` เวลาถูกบีบโดยรักษาอัตราส่วนเดิม
(heartbeat 1 วิ แทน 20 · stale 3.75 วิ = 3.75 จังหวะเต้นเท่าของจริง · drain cap 5 วิ ก่อนแก้ / 180 วิ หลังแก้ = อัตราส่วน 600 วิ : 6 ชม. เท่าเดิม · reap 15 วิ = 3 เท่าของ drain cap เดิม เหมือน 30 นาที : 600 วิ)
งานปลอมยาว 8 วินาที (ยาวกว่า drain cap เดิม) ไม่แตะ LLM/GPU จริง · ฝั่ง "ก่อนแก้" ใช้ `worker.py` ของ HEAD ดึงด้วย
`git show HEAD:meeting_ai/worker.py` แก้เฉพาะสองค่าเวลา

```
prefix : beats_after_claim=  1  worker ออกที่ 5.2s  งานตอนนั้น=running  สุดท้าย=queued   reaped=True
fixed  : beats_after_claim=  9  worker ออกที่ 9.2s  งานตอนนั้น=done     สุดท้าย=done     reaped=False
```

ไทม์ไลน์ของรอบ "ก่อนแก้":

```
t= 0.2s  CLAIM -> job = running
t= 4.0s  worker alive=False (job status=running)   <-- เซิร์ฟเวอร์เห็นเป็น 'gone' ทั้งที่งานยังทำอยู่
t= 5.2s  worker process ออกแล้ว (exit=0)           <-- งานค้างอยู่ที่ 55% เธรด daemon ถูกฆ่า
t=19.5s  *** REAPED: job กลับเข้าคิว (เงียบไป 15.2s > 15.0s)
```

รอบ "หลังแก้" ด้วยพารามิเตอร์ชุดเดียวกัน: heartbeat เดินต่อ 9 ครั้งระหว่างทำงาน, `alive=True` ตลอด,
งานส่งผลกลับที่ 8.3 วิ แล้ว worker ถึงออกที่ 9.2 วิ, reaper ไม่เคยทำงาน

**ยังไม่ได้พิสูจน์ด้วยการรันจริง** (อนุมานจากโค้ด/SQL เท่านั้น): เส้นทางกับ Postgres จริง (`pgstore.jobs_reap` ตัวเป็น ๆ)
เพราะเครื่องนี้ไม่มี Postgres และ `MAI_TEST_DATABASE_URL` ไม่ได้ตั้ง · งาน `kind='bot'` ที่ต้องจบเป็น `error` แทนการคืนคิว
(รีโปรใช้ `kind='summarize'` เพราะงานบอทต้องมี Docker) · เส้นทาง Ctrl+C (รีโปรใช้ `--once` ซึ่งตั้งธงใบเดียวกัน)

## ทางเลือกที่พิจารณาแล้วไม่เอา

1. **ให้เซิร์ฟเวอร์ผ่อนกฎ reap แทน (เพิ่มเวลา 30 นาที หรือไปดู `workers.last_seen` ประกอบ)** — ผิดที่ผิดทาง:
   ปัญหาคือ worker โกหกว่าตัวเองตายแล้วทิ้งงานจริง ๆ ยืดเวลาฝั่งเซิร์ฟเวอร์ = งานที่ worker ตายจริงค้างนานขึ้นทุกใบ
2. **ให้ `--once` ออกทันทีที่คว้างานได้ แล้วปล่อยให้งานเดินต่อในโปรเซสลูก / ไม่ต้องรอ** — เธรดงานเป็น daemon และผลลัพธ์ต้องยิงกลับผ่าน
   client เดียวกัน ทำแบบนั้นคืองานตายทันทีที่โปรเซสออก (คืออาการเดิมเป๊ะ)
3. **ให้เธรดงานเต้น heartbeat เอง** — ต้องแก้ทุก handler และ `_run_one` พังง่ายเมื่อมีหลายงานพร้อมกัน (บอทสูงสุด `--max-bots` ใบ)
   เธรด `beat()` ที่มีอยู่แล้วเห็น `active` ครบทุกใบอยู่แล้ว แค่มันออกเร็วเกินไป
4. **แยกธงใหม่ (`beating`/`draining`) เพิ่มอีกตัว** — สถานะจริงมีแค่ "หยุดรับงานใหม่แล้วหรือยัง" + "ยังมีงานค้างไหม" ซึ่งอ่านจาก
   `stopping["flag"]` กับ `active` ได้ตรง ๆ เพิ่มธงที่สามมีแต่จะเพี้ยนกันเอง
5. **ยกเพดานรองานทิ้งไปเลย (รอไม่จำกัด)** — งานที่ค้างเพราะ subprocess แขวน (ffmpeg/whisper/docker) จะทำให้ worker ไม่ยอมตายตลอดกาล
   และตัวตั้งเวลาจะมีโปรเซสซ้อนกันเรื่อย ๆ จึงเก็บเพดานไว้ แต่ให้ยาวพอกับงานจริง

## สิ่งที่แก้

1. `beat()` เต้นจนกว่าจะ **"ถูกสั่งหยุด และไม่มีงานค้าง"** (`stopping["flag"] and not active`) ไม่ใช่แค่ถูกสั่งหยุด
   — ตรวจเงื่อนไขนี้ทั้งก่อนเต้นและระหว่างหลับ (ทุก 0.5 วิ) เพื่อให้จบเร็วเมื่อไม่มีงานแล้ว
2. เพดานรองานตอนจะออกย้ายจากเลข `600` ที่ฝังในลูป มาเป็นค่าคงที่ระดับโมดูล `DRAIN_MAX_SEC = 6 * 3600`
   (งานบอทนั่งในห้องได้ถึง 180 นาที ตาม `runner.bot_job` `max_minutes` แล้วยังต้องถอดเสียง + สรุปต่อ)
   และนับด้วย `time.monotonic()` ไม่ใช่จำนวนรอบ (ของเดิม `range(600)` + `sleep(1)` ≠ 600 วินาทีจริง)
3. ครบเพดานแล้วยังมีงานค้าง → พิมพ์เตือนทาง stderr พร้อม **id ของงานที่ถูกทิ้งไว้** (ของเดิมออกเงียบ ๆ)

## Acceptance criteria

1. `worker --once` ที่คว้างานมาได้ ต้องยิง heartbeat ต่อไปตลอดช่วงที่งานยังทำอยู่ โดยช่องว่างระหว่างครั้งไม่เกิน
   `WORKER_STALE_SECONDS` (ค่าจริง 75 วิ = 3.75 จังหวะของ `HEARTBEAT_SEC`)
2. heartbeat ระหว่างนั้นต้องรายงาน `status="busy"` พร้อม id ของงานที่ถืออยู่ (หน้าเว็บอ่าน `job_id`/`job_title` จากตรงนี้)
3. `run()` ต้องไม่คืนค่าก่อนงานที่ค้างอยู่จะรายงานผล (`/result` หรือ `/error`) กลับไปแล้ว
4. เมื่อไม่มีงานค้างแล้ว เธรด heartbeat ต้องหยุด — ห้ามเต้นค้างต่อหลัง `run()` จบ
5. เพดาน `DRAIN_MAX_SEC` ยังบังคับใช้จริง: งานที่ค้างนานเกินเพดาน worker ต้องออกได้ และบอกทาง stderr ว่าทิ้งงาน id ไหนไว้
6. ค่า `DRAIN_MAX_SEC` ต้องครอบงานบอทที่ยาวที่สุดได้ (≥ 3 ชั่วโมง)
7. ชุดทดสอบเดิมยังผ่านครบ (baseline สาขานี้ = 264 tests, skipped 7)
