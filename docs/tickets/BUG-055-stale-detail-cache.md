# BUG-055 — แคชรายละเอียดการประชุมค้าง (โหมดไฟล์): "แก้แล้วไม่เซฟ"

**Severity:** P1 (ข้อมูลที่ผู้ใช้เพิ่งบันทึกหายไปจากหน้าจอ — ไฟล์บนดิสก์ถูกต้อง แต่ API ตอบของเก่า)
**Component:** `meeting_ai/web/store.py` (file mode เท่านั้น)
**Reported by:** owner (พบตอน integration-test สองสาขาพร้อมกัน) · **Fixed by:** backend-dev · **Date:** 2026-09-17
**Affects:** local mode ทุกเวอร์ชันที่มี `_detail_cache` · **Not affected:** cloud mode (`web/pgstore.py` ไม่มีแคช — `load_detail()` เรียก `get()` ซึ่งอ่าน Postgres ทุกครั้ง; ยืนยันด้วย `grep -n cache meeting_ai/web/pgstore.py` → ไม่มีผลลัพธ์)

## อาการที่ผู้ใช้เจอ

แก้ชื่อเรื่อง / เกลาสรุป / แก้บทถอดเสียง / สั่งแปลภาษา แล้วหน้าจอยังเป็นค่าเดิม เหมือน "กดบันทึกแล้วไม่เซฟ"
เกิดแบบสุ่ม (ไม่ใช่ทุกครั้ง) จึงเป็นบั๊กประเภทที่ไล่หากันได้นาน — ข้อมูลไม่ได้หาย ไฟล์ `<id>.json` ถูกต้องเสมอ
สิ่งที่ผิดคือสิ่งที่ API ตอบกลับทันทีหลังเขียน

## สาเหตุ (root cause)

`load_detail()` แคชรายละเอียดที่ parse แล้วโดยใช้ **mtime ของไฟล์** เป็นกุญแจตรวจความสด:

```python
cached = _detail_cache.get(mid)
if cached and cached[0] == mtime:
    return cached[1]
```

แต่ความละเอียดของ mtime หยาบกว่าจังหวะที่เราเขียนไฟล์มาก บนเครื่องผู้พัฒนา (Windows 11, NTFS)
เขียนไฟล์ 300 ครั้งติดกันได้ mtime ต่างกันเพียง **26 ค่า**, ช่องว่างสูงสุด **15.8 ms** (ความถี่อัปเดต
นาฬิการะบบ ~15.6 ms) และ `time.time() - st_mtime` ทันทีหลังเขียนคือ `0.0`

ลำดับที่ทำให้พัง (เกิดครบภายใน tick เดียว):

1. `set_translation()` เรียก `load_detail(mid)` → cache ได้ `(M, detail_เก่า)`
2. `_write_json(_detail_path(mid), detail_ใหม่)` → ไฟล์ใหม่ได้ mtime `M` เท่าเดิม (tick เดียวกัน)
3. `return get(mid)` → `load_detail()` เห็น `cached[0] == mtime` → **คืน `detail_เก่า`**

จุดที่เขียนไฟล์ detail มี 5 แห่ง (`create`, `set_translation`, `set_segments`, `set_summary`, `update`)
แต่มีที่เดียวที่ล้างแคชคือ `delete()` — ทุกเส้นทางเขียนจึงทิ้งแคชเก่าไว้ทั้งหมด

## ทางเลือกที่พิจารณา

| ทางเลือก | ปิดเคสในโพรเซสเดียว | ปิดเคสข้ามโพรเซส | ต้นทุน |
|---|---|---|---|
| A. `pop` แคชทุกจุดที่เขียน | ได้ | **ไม่ได้** — โพรเซสอื่นเขียนทับใน tick เดียวกับที่เราแคชไว้ เรายังตอบของเก่า | ต่ำ |
| B. write-through (ใส่สิ่งที่เพิ่งเขียนลงแคชพร้อม mtime ใหม่) | ได้ | **ไม่ได้ และแย่กว่า A** — เรา "ยืนยัน" ค่าที่อาจถูกโพรเซสอื่นเขียนทับไปแล้วใน tick เดียวกัน | ต่ำ |
| C. ตัดแคชทิ้ง | ได้ | ได้ | `search()` ต้องอ่านไฟล์ detail ทุกไฟล์ทุกครั้งที่ผู้ใช้พิมพ์ค้นหา (คลังใหญ่ = หลายสิบ MB ต่อคำค้น) |
| D. **แคชเฉพาะไฟล์ที่นิ่งแล้ว + ล้างแคชทุกจุดที่เขียน** | ได้ | ได้ | ต่ำ — เสียแค่การอ่านซ้ำของการประชุมที่เพิ่งถูกแก้ภายใน 2 วินาที |

เลือก **D**

เหตุผล: ต้นเหตุคือความละเอียดของ mtime ไม่ใช่การลืม `pop` — "เทียบ mtime ให้ละเอียดขึ้น"
(`st_mtime_ns`) ไม่ใช่การแก้ เพราะสองการเขียนใน tick เดียวกันได้ค่านาโนวินาทีเท่ากันอยู่ดี
ส่วน A/B แก้ได้เฉพาะโพรเซสตัวเอง แต่ file store **ไม่ได้รับประกันว่ามีโพรเซสเดียว** ตามสัญญา
(`mai web` กับ `mai transcribe`/`mai process` จาก CLI ใช้โฟลเดอร์เดียวกันได้) ถ้าเลือก A/B
เคส "แก้จาก CLI แล้วหน้าเว็บยังเห็นของเก่า" จะยังอยู่และไล่ยากกว่าเดิม

กติกาของ D: **แคชได้ก็ต่อเมื่อไฟล์ถูกแก้ครั้งสุดท้ายนานกว่า `_CACHE_MIN_AGE` แล้ว**

พิสูจน์ว่าปิดเคสข้ามโพรเซสจริง: ให้ `G` = ความละเอียดของ timestamp ของ filesystem และ
เก็บแคชเฉพาะเมื่อ `now - mtime >= G` ถ้าต่อมามีการเขียน (โพรเซสไหนก็ตาม) ที่เวลา `t >= now`
จะได้ stamp ใหม่ `floor(t/G)*G >= floor((mtime+G)/G)*G = mtime + G > mtime`
คือ **mtime ใหม่ต่างจากค่าที่แคชไว้เสมอ** → การอ่านครั้งถัดไป miss แล้วไปอ่านดิสก์
ตั้ง `_CACHE_MIN_AGE = 2.0` เพราะ FAT32/exFAT มี `G = 2 s` (หยาบที่สุดที่เจอได้จริง;
NTFS/ext4 ละเอียดกว่ามาก) และกฎเดียวกันนี้ยังปิด race ในโพรเซสเดียวด้วย: เธรดที่อ่านไฟล์
ค้างอยู่ตอนเธรดอื่นเขียน จะเขียนแคชกลับภายใต้ mtime เก่า ซึ่งการอ่านครั้งถัดไปจะ miss เอง

ข้อจำกัดที่ยอมรับ: ถ้านาฬิกาเครื่องถูกปรับ **ถอยหลัง** เกิน 2 วินาทีระหว่างการเขียนสองครั้ง
แคชอาจค้างได้อีก — จึงคง `pop` ฝั่งเขียนไว้ด้วย (ทางเลือก A) เพื่อให้เคสในโพรเซสเดียวถูกต้อง
โดยไม่พึ่งพฤติกรรมของนาฬิกาเลย ทั้งสองอย่างรวมกันคือสิ่งที่ implement

## สิ่งที่แก้

`meeting_ai/web/store.py` เท่านั้น:

1. เพิ่ม `_write_detail(mid, detail)` — เขียนไฟล์ detail แล้ว `_detail_cache.pop(mid, None)` เสมอ
   ใช้แทน `_write_json(_detail_path(mid), detail)` ทั้ง 5 จุด (`create`, `set_translation`,
   `set_segments`, `set_summary`, `update`) เพื่อให้ "เขียน detail" มีทางเดียวที่ล้างแคชในตัว
2. `load_detail()` เก็บลงแคชเฉพาะเมื่อ `time.time() - mtime >= _CACHE_MIN_AGE` (2.0 s)
   กรณีอื่นให้ `pop` ทิ้ง (รวมถึงตอนไฟล์หาย) — ยังคืนค่าที่อ่านจากดิสก์ตามปกติ

ไม่แตะ `pgstore.py` (ไม่มีแคช) ไม่แตะ `server.py` ไม่เปลี่ยน API/สคีมา ไม่มี dependency ใหม่

## เกณฑ์ผ่าน (acceptance)

- วนเขียน `set_translation()` 100 ครั้งแล้วอ่านกลับทุกครั้ง → `stale_reads = 0` (ก่อนแก้ = 15)

## `_load_index()` / `_save_index()` — ตรวจแล้ว เป็นคนละปัญหา

**ไม่มีบั๊กทรงเดียวกัน**: ทั้งคู่ไม่มีแคชเลย `_load_index()` เรียก `_read_json(INDEX_PATH, …)`
อ่านดิสก์ทุกครั้ง และ `_write_json()` เขียนแบบ atomic (`tmp` + `os.replace`) จึงไม่มีทั้งค่าค้างและไฟล์ฉีก

แต่พบ **ข้อบกพร่องคนละตัว** ในบริเวณเดียวกัน ขอส่งต่อ `bug-triager` แทนการแก้เงียบ ๆ:

- **lost update ของ `index.json` ข้ามโพรเซส** — ทุกฟังก์ชันทำ read-modify-write
  (`_load_index()` → แก้ → `_save_index()`) ภายใต้ `_lock` ซึ่งเป็น `threading.RLock`
  **ในโพรเซสเดียวเท่านั้น** ไม่มี file lock ถ้า `mai web` กับ CLI แก้คนละการประชุมพร้อมกัน
  ตัวที่เขียนทีหลังจะเขียนทั้งไฟล์ทับ → การแก้ของอีกฝั่งหายทั้งรายการ
  (ต่างจาก BUG-055 ตรงที่ข้อมูล **หายจริงบนดิสก์** ไม่ใช่แค่แคชค้าง)
- `update()` เขียน `_save_index()` เสมอแม้ `title`/`summary` เป็น `None` ทั้งคู่ (เขียนเปล่า) — เล็กน้อย
