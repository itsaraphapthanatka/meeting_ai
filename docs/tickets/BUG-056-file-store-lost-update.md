# BUG-056 — Lost update ใน file store เมื่อมีสองโพรเซสเขียนพร้อมกัน

- **Severity:** P1 (BACKLOG #56) — รุนแรงกว่า #55 เพราะ #55 อ่านได้ข้อมูลเก่า ส่วนอันนี้ **ลบงานที่เขียนสำเร็จไปแล้วทิ้ง**
- **Owner:** backend-dev (verify: test-engineer เขียน regression test, code-reviewer)
- **Status:** **fixed (uncommitted)** 2026-09-17
- **Scope:** `meeting_ai/web/store.py` เท่านั้น (โหมดไฟล์) — โหมด cloud ใช้ `pgstore.py` + transaction ของ Postgres ไม่เกี่ยวข้อง

## อาการ
ผู้ใช้เปิดหน้าเว็บ (`mai web`) ค้างไว้ แล้วรัน `mai process` / `mai bot` ในเทอร์มินัลอีกอัน = สองโพรเซสเขียน `recordings/web/` พร้อมกันทันที ผลคือ

- การประชุมที่เพิ่งบันทึกเสร็จ **หายไปจาก index** (ไม่ได้ลบไฟล์ `<id>.json` แต่ไม่มีใน `index.json` = มองไม่เห็น กู้คืนได้ด้วยมือเท่านั้น)
- คำแปล/บทถอดเสียงที่แก้ไว้ **ถูกทับหาย** ถ้ามีสองคน/สองโพรเซสแก้การประชุมเดียวกัน
- บน Windows ยังได้ `PermissionError` ดิบ ๆ ขึ้นมาถึง handler = **500** (ดูข้อ 2)

## Root cause

**1. ล็อกเป็นแบบ process-local** — [store.py:26](../../meeting_ai/web/store.py#L26) `_lock = threading.RLock()` กันได้แค่เธรดในโพรเซสเดียวกัน ทุกฟังก์ชันเขียนเป็น read-modify-write เต็มไฟล์:

```
A: _load_index() -> 10 รายการ
B: _load_index() -> 10 รายการ
A: insert #11 -> _save_index() -> ดิสก์มี 11
B: insert #12 -> _save_index() -> ดิสก์มี 11 (ของ A หายถาวร)
```

`_write_json` atomic ต่อ 1 การเขียน (tmp + `os.replace`) ไฟล์จึงไม่เคยฉีกครึ่ง — แต่ atomic ไม่ได้แปลว่า serializable ช่วงที่เสียคือช่วง "อ่านแล้วยังไม่เขียน"

ไฟล์ detail มีรูปแบบเดียวกันเป๊ะ: `set_translation`, `set_segments`, `set_summary`, `update` ทำ `load_detail(mid)` → แก้ dict → เขียนทับทั้งก้อน สองโพรเซสแปลภาษาต่างกันพร้อมกัน = เหลือภาษาเดียว

**2. ชื่อไฟล์ tmp ชนกันข้ามโพรเซส (เจอระหว่างทำ repro)** — [store.py:61](../../meeting_ai/web/store.py#L61) ใช้ `path.with_suffix(path.suffix + ".tmp")` = `index.json.tmp` ชื่อเดียวกันทุกโพรเซส บน Windows โพรเซส B เปิดเขียน tmp ขณะที่ A กำลัง `os.replace` ไฟล์เดียวกัน → `PermissionError` โยนทะลุขึ้นไปถึง request handler (วัดได้ ~50% ของการเรียกในโหลดที่ทดสอบ) นี่คือ 500 ที่คาดเดาได้ = บั๊ก

**3. แคช detail ตาม mtime ทำให้ล็อกไม่มีความหมาย** — `load_detail` เสิร์ฟค่าจากแคชในหน่วยความจำ ต่อให้ล็อกข้ามโพรเซสสำเร็จ ค่าที่อ่านมาแก้ก็ยังเป็นค่าก่อนหน้าที่โพรเซสอื่นเขียนไปแล้ว (นี่คือ BACKLOG #55 คนละใบ) → การแก้ใบนี้ต้องบังคับให้ "อ่านสดจากดิสก์" ภายในเขตล็อกด้วย ไม่งั้นล็อกก็แค่ทำให้ช้าลงเฉย ๆ

## Reproduction (วัดจริง ก่อนแก้)
สคริปต์ spawn โพรเซสลูกจริง 4 ตัว (ไม่ใช่เธรด) ยิงใส่ store เดียวกัน มี barrier แบบไฟล์ให้เริ่มพร้อมกัน แล้วนับสิ่งที่ "เขียนสำเร็จ" เทียบกับสิ่งที่เหลืออยู่บนดิสก์

```
index  : 4 procs x 25 creates x 5 รอบ  -> เขียนสำเร็จ 268 จาก 500, LOST 152, PermissionError 252
detail : 4 procs x 25 set_translation x 5 รอบ -> เขียนสำเร็จ 223 จาก 500, LOST 165, PermissionError 297
```

อ่านตัวเลขนี้ว่า: ครึ่งหนึ่งของคำสั่งพัง (500) และเกินครึ่งของคำสั่งที่ **ตอบผู้ใช้ว่าสำเร็จแล้ว** หายไปจากดิสก์

## สิ่งที่ต้องทำ
- (ก) ล็อกข้ามโพรเซสด้วย stdlib — `msvcrt.locking` (Windows) / `fcntl.flock` (POSIX) หลังเฮลเปอร์ตัวเดียว ล็อกไฟล์เดียวทั้ง store (`recordings/web/.store.lock`) ไม่ใช่ล็อกต่อไฟล์ เพราะ `create` แตะทั้ง detail และ index — ล็อกหลายตัวต้องมีลำดับการจับและเสี่ยง deadlock โดยได้ throughput เพิ่มมาน้อยมาก (การเขียนเกิดไม่กี่ครั้งต่อการประชุม)
- (ข) ล็อกต้องครอบ **ทั้ง read-modify-write** ไม่ใช่แค่ตอนเขียน และต้องซ้อนได้ (`set_translation` → `get` → `_load_index`)
- (ค) ลำดับการจับล็อกคงที่: `threading.RLock` ก่อนเสมอ แล้วค่อยล็อกไฟล์ (รวมไว้ใน context manager ตัวเดียวเพื่อไม่ให้ call site จับสลับลำดับได้) — เธรดในโพรเซสเดียวกันจึงเข้าเขตล็อกไฟล์ได้ทีละเธรด ไม่มีโอกาส deadlock ระหว่างล็อกสองชั้น
- (ง) ล้างแคช detail ตอนเข้าและออกจากเขตล็อก (เข้า: ระหว่างที่เรารอ โพรเซสอื่นอาจเขียนไปแล้ว / ออก: ค่าที่เราเพิ่งเขียนอาจ mtime ชนกับของเดิม) — ห้ามใช้ mtime ตัดสินใจอะไรทั้งสิ้น (บทเรียนจาก #55: เขียนติดกัน 300 ครั้งได้ mtime ต่างกันแค่ 14 ค่า)
- (จ) ชื่อไฟล์ tmp ต้องไม่ชนข้ามโพรเซส (ใส่ pid) — ปิดข้อ 2 และทำให้เส้นทาง degrade (ข้อ ฉ) ไม่พังด้วย
- (ฉ) ห้ามค้างตลอดกาล

## Timeout / failure policy (ตัดสินใจแล้ว)
- รอล็อกได้สูงสุด **10 วินาที** (`LOCK_TIMEOUT`) แบบ non-blocking + polling ถอยหลังเป็นขั้น 1 ms → 50 ms เขตวิกฤตจริงกินเวลาระดับมิลลิวินาที 10 วินาทีจึงแปลว่ามีอะไรผิดปกติ ไม่ใช่แค่คิวยาว
- **เจ้าของล็อกตายไม่ทำให้ค้าง** ทั้ง `msvcrt.locking` และ `flock` ผูกกับ file handle ระบบปฏิบัติการปล่อยล็อกให้เองเมื่อโพรเซสตาย (ไม่มี stale lock file ให้ต้องเก็บกวาด และเราไม่ลบไฟล์ล็อกทิ้ง เพราะการลบไฟล์ที่โพรเซสอื่นถือ handle อยู่คือแหล่ง race ใหม่)
- **ครบ 10 วินาทีแล้วไม่ได้ล็อก → เขียนต่อโดยไม่มีล็อก** พร้อม warning ภาษาอังกฤษลง stderr (คอนโซลเครื่องเจ้าของเป็น cp874 — ข้อความ debug ห้ามเป็นไทย) เหตุผล: ทางเลือกคือโยน exception ซึ่งกลายเป็น 500 และ **ทิ้งงานของผู้ใช้ทั้งก้อน** (บทถอดเสียงที่เพิ่งถอดมา 40 นาที) การเขียนแบบไม่มีล็อกคือพฤติกรรมเดิมของระบบ = แย่ที่สุดเท่ากับก่อนแก้ ไม่ได้แย่ลง ส่วนการปฏิเสธการเขียนคือทำให้ผู้ใช้เสียข้อมูลแน่นอน 100% จึงเลือก availability
- เปิดไฟล์ล็อกไม่ได้เลย (สิทธิ์/AV/โฟลเดอร์ถูก mount แบบแปลก) ก็ใช้นโยบายเดียวกัน: warn แล้วเขียนต่อ store ต้องไม่ล่มเพราะล็อกไฟล์

## ขอบเขตที่ทำให้ปลอดภัย (ระบุตามที่ขอ)
| ฟังก์ชัน | เดิม | ตอนนี้ |
|---|---|---|
| `create` | RLock | RLock + file lock (detail + index ในเขตเดียว) |
| `set_translation` | RLock | RLock + file lock |
| `set_segments` | RLock | RLock + file lock |
| `set_summary` | RLock | RLock + file lock |
| `update` | RLock | RLock + file lock |
| `delete` | RLock | RLock + file lock (index + ลบไฟล์ในเขตเดียว) |
| `set_setting` | RLock | RLock + file lock (settings.json ก็เป็น RMW) |
| `get`, `search`, `stats`, `get_setting`, `load_detail` | RLock | **ไม่เปลี่ยน — อ่านอย่างเดียว ไม่จับล็อกไฟล์** |

เหตุผลที่ฝั่งอ่านไม่จับล็อก: ล็อกที่ stdlib ให้มาบน Windows เป็น exclusive อย่างเดียว (ไม่มี shared lock ที่พกพาข้ามระบบได้) ถ้าให้ผู้อ่านจับด้วย ทุก `GET /api/meetings` จะไปต่อคิวกับงานเขียน ผลคือหน้าเว็บช้าลงโดยได้ความถูกต้องเพิ่มมาน้อย — แต่ละไฟล์ที่ผู้อ่านเห็นยังเป็นไฟล์สมบูรณ์เสมอเพราะ `os.replace` เป็น atomic สิ่งที่ยังไม่การันตีคือ "index กับ detail เป็น snapshot เดียวกัน" ซึ่งเป็นพฤติกรรมเดิมและไม่ทำให้ข้อมูลหาย

## Acceptance criteria
1. โพรเซสแยกจริง ≥ 4 ตัว × ≥ 100 การเขียนต่อสถานการณ์ → **LOST = 0** ทั้งกรณี index (`create`) และ detail (`set_translation`) ก่อนแก้ต้องเห็นตัวเลขหายจริง
2. ไม่มี `PermissionError`/exception หลุดออกจาก store ในโหลดเดียวกัน
3. ไม่มี deadlock และเรียกซ้อนกันได้ (`set_translation` เรียก `get` ต่อท้าย, `create` เรียก `_load_index`)
4. โหมด cloud ไม่เปลี่ยนพฤติกรรม — `pgstore.py` ไม่ถูกแตะ และไม่มี call site ใหม่ที่ต้องมีคู่แฝดใน pgstore (ล็อกอยู่ภายใน `store.py` ล้วน ไม่ใช่ public API)
5. ชุดทดสอบเดิม 64 tests ยังผ่าน (1 skipped) และ `python -m compileall -q meeting_ai api bot` ผ่าน
6. ต้นทุนโหมดโพรเซสเดียว: overhead ต่อการเขียน ≤ 1 ms (วัดจริง ใส่ตัวเลขใน resolution)

## Resolution — fixed (uncommitted) 2026-09-17

**ไฟล์ที่แก้: 1 ไฟล์** `meeting_ai/web/store.py` (+154/-10) · `pgstore.py` ไม่ถูกแตะแม้แต่บรรทัดเดียว

- `_store_lock_path()` คืน `WEB_DIR / ".store.lock"` **คำนวณตอนเรียก ไม่ใช่ตอน import** — ตั้งใจ ไม่ใช่สไตล์: `tests/_harness.py` แพตช์ `WEB_DIR`/`INDEX_PATH`/`SETTINGS_PATH` ทีหลัง ถ้าผูกค่าตอน import ไฟล์ล็อกของเทสจะไปโผล่ใน `recordings/web/` ตัวจริงของเจ้าของเครื่อง (กับดักเดียวกับที่ทำให้ต้องแพตช์ 3 ตัวใน harness)
- `_file_lock()` context manager — นับความลึกรองรับการเรียกซ้อน (จับจริงเฉพาะชั้นนอกสุด), `msvcrt.locking(LK_NBLCK)` / `fcntl.flock(LOCK_EX|LOCK_NB)` วน polling 1 ms → 50 ms จนถึง `LOCK_TIMEOUT`, ล้าง `_detail_cache` ทั้งตอนเข้าและตอนออก
- `_guard()` = `with _lock: with _file_lock():` — call site มีทางเดียว จับสลับลำดับไม่ได้ ฟังก์ชันเขียน 7 ตัวเปลี่ยนมาใช้ตัวนี้ ฝั่งอ่านไม่แตะ
- `_LOCK_KIND` เลือกกลไกครั้งเดียวตอน import ถ้าไม่มีทั้ง `msvcrt` และ `fcntl` จะ **ไม่** วนรอล็อกที่ไม่มีวันได้ (ไม่งั้นทุกการเขียนจะช้าลง 10 วินาที)
- `_write_json` ใส่ pid ในชื่อ tmp (`index.json.31544.tmp`) + retry `os.replace` (ดูด้านล่าง)

### สิ่งที่เจอเพิ่มระหว่างพิสูจน์ (แก้ไปด้วย เพราะไม่แก้แล้วการแก้หลักไม่มีผลจริง)
**ผู้อ่านจากอีกโพรเซสทำให้ `os.replace` ของผู้เขียนพังบน Windows** — `MoveFileEx` ล้มเป็น `PermissionError` ถ้าไฟล์ปลายทางถูกโพรเซสอื่น "เปิดอ่าน" ค้างอยู่ (Python เปิดไฟล์โดยไม่ขอ `FILE_SHARE_DELETE`) การทดลองแยก: ผู้อ่าน 2 โพรเซสยิงต่อเนื่อง ทำให้ผู้เขียน `os.replace` ล้ม **6,220 จาก 7,492 ครั้ง (83%)** นี่คือหน้าเว็บที่เปิดค้างไว้ (poll ทุก 1.5 วิ) กับ `mai process` ที่เพิ่งถอดเสียงเสร็จ — ล็อกอย่างเดียวไม่ช่วย เพราะผู้อ่านไม่ได้จับล็อก ปิดด้วย retry `PermissionError` อย่างเดียว (ENOSPC ฯลฯ เด้งทันที) ในกรอบ `REPLACE_TIMEOUT = 2.0` วินาที ถอยหลัง 1 ms → 20 ms หมดเวลาแล้วยังไม่ได้จึงค่อยโยน (ปล่อย `.tmp` ค้างไว้ตั้งใจ — ข้างในคือข้อมูลใหม่ที่กู้ด้วยมือได้)

### ผลวัดจริง (เครื่องเดียวกัน สคริปต์เดียวกัน โพรเซสลูกจริงทั้งหมด มี barrier ให้เริ่มพร้อมกัน)

| สถานการณ์ | ก่อนแก้ | หลังแก้ |
|---|---|---|
| index — 4 procs × 25 × 5 รอบ | สำเร็จ 268/500 · **LOST 152** · error 252 | สำเร็จ **500/500** · **LOST 0** · error 0 |
| detail — 4 procs × 25 × 5 รอบ | สำเร็จ 223/500 · **LOST 165** · error 297 | สำเร็จ **500/500** · **LOST 0** · error 0 |
| index — 6 procs × 100 × 3 รอบ | (ไม่ได้วัด) | สำเร็จ **1800/1800** · **LOST 0** · error 0 |
| detail — 6 procs × 100 × 3 รอบ | (ไม่ได้วัด) | สำเร็จ **1800/1800** · **LOST 0** · error 0 |
| ผสม index — 3 writers + 2 readers × 100 × 3 รอบ | สำเร็จ 376/900 · **LOST 110** · error 524 | สำเร็จ **900/900** · **LOST 0** · error 0 (อ่านไปด้วย 15,198 ครั้ง) |
| ผสม detail — 3 writers + 2 readers × 100 × 3 รอบ | สำเร็จ 388/900 · **LOST 210** · error 512 | สำเร็จ **900/900** · **LOST 0** · error 0 (อ่านไปด้วย 53,524 ครั้ง) |

"สำเร็จ" = ครั้งที่ store ตอบกลับว่าบันทึกแล้ว "LOST" = ในจำนวนนั้น มีกี่รายการที่หายไปจากดิสก์ตอนจบ
รวมหลังแก้ **6,400 การเขียนจากโพรเซสแยกจริง หายศูนย์ พังศูนย์** (รอบสุดท้ายที่รันกับโค้ดชุดที่ส่งจริง 5,400 ครั้ง)

### ขอบที่ตรวจเพิ่ม
- **เธรดในโพรเซสเดียว** 10 เธรด × 30 `create` → 300 รายการ หายศูนย์ ไม่มีเธรดค้าง (2.2 วิ) = ล็อกสองชั้นไม่ deadlock กันเอง
- **เรียกซ้อน** `_guard()` ซ้อน `_guard()` แล้วเขียนได้ปกติ `_lock_depth` กลับเป็น 0 เมื่อออก
- **timeout** โพรเซสอื่นถือล็อกค้าง (ตั้ง `LOCK_TIMEOUT = 1.0` เพื่อทดสอบ) → รอ 1.03 วิ พิมพ์ `meeting_ai.store: store lock busy for 1.0s; writing without it` ลง stderr แล้ว **บันทึกสำเร็จ** ไม่มี exception ถึงผู้ใช้
- **เจ้าของล็อกตาย** ฆ่าโพรเซสที่ถือล็อกอยู่ → การเขียนครั้งถัดไปได้ล็อกใน **0.00 วิ** ไม่มี stale lock ให้เก็บกวาด ไฟล์ `.store.lock` ค้างไว้ (ตั้งใจ) และไม่มี `.tmp` ตกค้าง

### สิ่งที่ยังไม่ได้ทำ / ฝากต่อ
- **regression test เป็นของ test-engineer** (ไม่ได้เขียนในใบนี้ตามที่ตกลง) สคริปต์พิสูจน์เป็นไฟล์ชั่วคราวใน scratchpad ไม่ได้ commit โครงที่แนะนำ: spawn `sys.executable` ลูกหลายตัว + barrier แบบไฟล์ + นับรายการที่เขียนสำเร็จเทียบกับ `index.json` / `translations` และอย่าลืมเคสผสม writer + reader (เคสนี้เป็นเคสที่จับบั๊ก `os.replace` ได้)
- **ชุดทดสอบ 64 tests เดิมไม่แตะเส้นทางเขียนของ file store เลย** — พิสูจน์ระหว่างทาง: แพตช์รอบแรกใช้ค่าคงที่ผิด (`msvcrt.LOCK_NBLCK` ซึ่งไม่มีจริง ชื่อถูกคือ `LK_NBLCK`) ทุก `store.create` จะ `AttributeError` แต่ **ชุดทดสอบยังผ่าน 64/64** สคริปต์หลายโพรเซสเป็นตัวจับได้ ช่องว่างนี้ควรอยู่ในคิวของ test-engineer
- **ยังไม่ปิดในใบนี้**: ผู้อ่านอาจเห็น `index.json` ใหม่คู่กับ `<id>.json` เก่าเสี้ยววินาที (ไม่ใช่ข้อมูลหาย) · BACKLOG #55 (แคช mtime ฝั่งอ่าน) ยังเป็นใบแยก ใบนี้แค่บังคับให้ **เส้นทางเขียน** ไม่เชื่อแคชแล้ว (ล้างแคชตอนเข้า/ออกเขตล็อก) — ถ้า #55 merge ทีหลัง จุดที่ชนกันคือส่วนหัวของไฟล์กับ `load_detail` เท่านั้น ทั้งสองแพตช์ทำงานร่วมกันได้ ไม่ทับหน้าที่กัน
- **เจ้าของต้องรันบน production:** ไม่มี — ใบนี้ไม่มี migration ไม่มี SQL และโหมด cloud (Vercel + Postgres) ไม่ได้รับผลกระทบ ตรวจแล้วไม่ใช่สมมติฐาน: `backend.py` เลือก `pgstore` ตอน import และไม่มีโมดูลใดนอก `backend.py` import file store ตรง ๆ (`server.py`/`exports.py` ใช้ `from .backend import store`, `jobs.py` ใช้ `from .backend import cloud, store`)
