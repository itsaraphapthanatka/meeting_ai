# BUG-059 — CI แดงบน `test (windows-latest)`: เทสต์ 2 ตัวใน `test_bug_011_body_size_caps.py` เปราะเมื่อ CPU ถูกแย่ง

- **Severity:** ไม่ใช่ P0/P1 ของแอป — เป็นความเปราะของ **ฮาร์เนสเทสต์เอง** (`tests/_harness.py`) ไม่ใช่บั๊กของ `meeting_ai/web/server.py`
- **Owner:** test-engineer
- **Status:** fixed 2026-09-17 (เฉพาะไฟล์ใน `tests/` — ไม่แตะ `meeting_ai/web/server.py`)
- **Files:** `tests/_harness.py`, `tests/test_bug_011_body_size_caps.py`

## อาการที่รายงานมา

`.github/workflows/ci.yml` job `test (windows-latest)` แดงเป็นระยะที่:

1. `TestBug011ConnectionCloseOn413.test_bug_011_413_has_connection_close_header_and_server_stays_healthy`
   — assertion เรื่อง 413 + `Connection: close` **ผ่าน** แล้วตายที่บรรทัดถัดมา `self.get("/api/config")`
   ด้วย `TimeoutError: timed out` (timeout 20 วินาทีของ `_harness._do`)
2. `TestBug011RequestSmugglingSingleResponse.test_bug_011_keepalive_still_yields_two_responses_for_two_plain_gets`
   — `AssertionError: 0 != 2 : b''` (ไม่ได้ไบต์ตอบกลับมาเลยภายใน `raw_send_and_collect(..., timeout=1.0)`)

## สาเหตุ (ยืนยันแล้วด้วยการรันจริง, ไม่ใช่การเดา)

`tests/_harness.py::_HttpCaseMixin._start_server()` (ก่อนแก้) สร้าง `server.Server(...)` (ซึ่ง
bind()+listen() เสร็จในตัว constructor แล้ว) แล้ว `thread.start()` **คืนค่าทันที** โดยไม่มี
readiness probe — คอนเนกชันใหม่เข้า backlog ของ OS ได้ทันที แต่ยังไม่มีใครตอบจนกว่าเธรด
`serve_forever` จะได้ CPU มา `accept()`/dispatch จริง เมื่อ CPU ถูกแย่งหนัก (เช่น CI runner อื่น
แชร์โฮสต์เดียวกัน antivirus scan, หรือ process อื่นบนเครื่อง) ช่วงว่างนี้เกินเพดานเวลาคงที่สั้นๆ
ที่ทั้งสองเทสต์นี้ใช้ (`_do` default 20s, `raw_send_and_collect` default 1.0-1.5s) — **ทั้งสองเพดาน
เป็น socket timeout เดี่ยวและเพดานรวมในตัวเดียวกัน** ไม่มีการ retry จึงยอมแพ้ทันทีที่ recv() รอบ
แรกหมดเวลา

**ยืนยันว่าเป็นของเดิมบน `main` ไม่ใช่ของสาขาใหม่**: รันชุด `test_bug_011_body_size_caps.py`
(subset 6 เทสต์ที่เกี่ยวข้อง) ขณะอัด CPU เต็มทุกคอร์ด้วยสคริปต์โหลด (`n = cpu_count()*2` =
20 process บนเครื่อง 10 คอร์) 6 รอบ **ก่อนแก้อะไรเลย** → **ล้ม 6/6 รอบ ตัวเดียวกัน บรรทัดเดียวกัน
เป๊ะ** ตรงกับที่รายงานมาทุกประการ (`TimeoutError: timed out` / `0 != 2 : b''`)

## สิ่งที่แก้ (เฉพาะ `tests/`)

### 1. `_HttpCaseMixin._start_server()` — เพิ่ม readiness probe

วนยิง `GET /api/config` จริงผ่าน `http.client` จนกว่าจะได้ 200 หรือหมดเวลาใจกว้าง (`180s`) —
ถ้าหมดเวลาแล้วยังไม่ตอบ `self.fail()` ด้วยข้อความชัดเจน (ไม่ปล่อยให้เทสต์ข้างล่างตายแบบงงๆ)
ต้นทุน "cold start ตอน CPU ไม่ว่าง" ถูกดูดซับไว้ใน `setUp()` (ยังไม่มี assertion ใดๆ) แทนที่จะ
ไปโผล่เป็นความล้มเหลวที่ดูเหมือนไม่เกี่ยวกับสิ่งที่เทสต์นั้นทดสอบจริงๆ

### 2. `raw_send_and_collect()` — รอ "จนครบจำนวนคำตอบที่คาด" ไม่ใช่ "รอเวลาคงที่"

เพิ่มพารามิเตอร์ `expect: int | None` และ `settle: float` — เมื่อระบุ `expect` ฟังก์ชันจะ
`recv()` แบบสั้นๆ วนซ้ำจนกว่าจะนับ `HTTP/1.1 ` ครบ `expect` ครั้ง (ไม่ใช่รอ timeout คงที่)
ภายในเพดานเวลารวมที่ผู้เรียกกำหนด (`timeout=`, ใจกว้างกว่าเดิมมาก) จากนั้น **รอต่ออีก `settle`
วินาที** ก่อนปิด socket

**ข้อควรระวังที่สำคัญที่สุด (ตามที่ผู้ว่าจ้างเตือนไว้)**: เทสต์ควบคุมกฎ
(`test_bug_011_smuggling_*_yields_one_response`, คาด 1 คำตอบ) ต้องพิสูจน์ได้ว่า "ไม่มีคำตอบที่
สองตามมา" — ถ้าหยุดอ่านทันทีที่เห็นคำตอบแรกโดยไม่รอ `settle` ต่อ เทสต์จะผ่านแบบไม่มีความหมาย
ยืนยันด้วยการทดลองจริง: `settle=0.5` เดิมสั้นเกินไปแม้บนเครื่องว่าง — เซิร์ฟเวอร์ใช้เวลามากกว่า
0.5 วินาทีเล็กน้อยกว่าจะวน loop กลับไปแปลง byte ที่ค้างอยู่ (nested GET) เป็นคำขอที่สอง ทำให้เทสต์
non-vacuous-proof (ย้อนกฎ `_send()` กลับไปเป็นแบบเดิมที่ไม่ปิดคอนเนกชันเมื่อ body ยังไม่ถูกอ่าน
จนหมด) **ยังผ่านอยู่แบบผิดๆ** ก่อนขยับ `settle` เป็น `1.5` วินาที — เก็บบทเรียนนี้ไว้ใน
`.claude/agent-memory/test-engineer/`

### 3. คำตอบของคำถาม "ตอบช้า หรือ ไม่ตอบเลย" (วัดจริง ไม่ได้เดา)

**ตอบช้า ไม่ใช่ไม่ตอบเลย** — ยืนยันด้วยสองวิธี:

- สคริปต์วัดตรง (`measure_ready.py`, สร้างเซิร์ฟเวอร์ใหม่ ยิง `GET /api/config` ซ้ำๆ ทุก 50ms
  จนสำเร็จ, ไม่เคยแตะ endpoint ของบั๊ก 413 เลย): ทั้ง 5 trial สุดท้ายจบไว (~0.3-0.4 วินาที) แต่
  **trial แรกใช้เวลา 89.3 วินาที** ก่อนได้คำตอบ 200 ครั้งแรก
- รันชุดเทสต์ที่แก้แล้วซ้ำขณะอัด CPU เต็มทุกคอร์ต่อเนื่อง 300 วินาที: ทุกครั้งที่ readiness probe
  ในที่สุดก็สำเร็จ (ได้ 200) การเรียกครั้งถัดไปในเทสต์เดียวกัน/เทสต์ถัดไปเร็วปกติทันที ไม่มีครั้งไหน
  ที่เซิร์ฟเวอร์ "ไม่ตอบเลย" อย่างถาวร — เมื่อโหลด CPU สิ้นสุดหรือช่วง spawn-storm ผ่านไป เซิร์ฟเวอร์
  กลับมาตอบปกติเสมอ **ไม่ใช่บั๊กค้าง/deadlock ของ `server.py`** และไม่ใช่ปัญหาเฉพาะ "หลังตอบ 413"
  ตามที่ตั้งสมมติฐานไว้ตอนแรก (`measure_ready.py` ไม่เคยส่ง request ที่ทำให้เกิด 413 เลย แต่ก็เจอ
  ความล่าช้าแบบเดียวกันตั้งแต่การเชื่อมต่อครั้งแรกสุดของเซิร์ฟเวอร์ที่เพิ่งสร้างใหม่)

**สรุป: ไม่พบบั๊ก P1 ใหม่ในแอป** — ปัญหาทั้งหมดคือการรอคอยของฮาร์เนสเทสต์ที่ไม่ยืดหยุ่นพอ

## ความเสี่ยงที่เหลือ (บอกตรงๆ ไม่กลบไว้)

ระดับโหลดที่ใช้ยืนยัน (`n = cpu_count()*2` = 20 process กิน CPU ล้วน รันต่อเนื่อง 300 วินาทีบน
เครื่อง dev 10 คอร์เครื่องนี้) ทำให้เกิด **"spawn storm"** ช่วงสั้นๆ ที่ยาวไม่คงที่มาก — วัดได้ตั้งแต่
~89 วินาที ถึงกว่า **300 วินาที** (round 1 ของเซสชันยืนยันสุดท้ายที่ deadline=180s ยัง fail: สอง
เทสต์ในรอบนั้นรวมกันกิน 305 วินาที มีอย่างน้อยหนึ่งเทสต์ชนเพดาน 180s เต็มๆ) **นี่ไม่ใช่การรับประกัน
100%**: บนเครื่องนี้ ถ้ารอบทดสอบบังเอิญเริ่มพร้อมกับโมเมนต์ที่ 20 โปรเซสถูกสปอว์นพอดี (ซึ่งเกิดขึ้น
กับ "round 1" ของทุกเซสชันยืนยันที่ทำมา เพราะสคริปต์ repro เริ่มรันแทบจะพร้อมกับสคริปต์โหลด) เทสต์
จะยัง fail ได้แม้ deadline จะใจกว้างแค่ไหนก็ตาม เนื่องจากยังไม่เคยวัดขอบบนที่แน่นอนของ storm นี้ได้
— แต่**ทุกรอบถัดไปในเซสชันเดียวกัน (ที่ไม่ได้เริ่มพร้อมโมเมนต์สปอว์นพอดี) ผ่านสะอาดทุกครั้งไม่มี
ข้อยกเว้น** (5/6, 6/6, 6/6 ตามลำดับ 3 เซสชัน หลัง round 1) และ error ที่เกิดขึ้นมาจาก
`_wait_until_ready()` เองพร้อมข้อความชัดเจนเสมอ ไม่ใช่ timeout ที่งงๆ เหมือนเดิม

**เหตุผลที่เชื่อว่าไม่กระทบ CI จริงของ GitHub Actions**: `windows-latest` runner เป็น VM เดี่ยว
ไม่มีกระบวนการอื่นมาแย่ง CPU 20 ตัวพร้อมกันแบบที่สคริปต์โหลดจำลอง (ดู `.github/workflows/ci.yml`
`timeout-minutes: 15` ต่อ job) ความล่าช้าที่เกิดขึ้นจริงบน CI น่าจะมาจาก scheduler jitter ระดับ
วินาทีถึงสิบวินาที ไม่ใช่ระดับนาทีแบบที่ทดลองนี้จำลอง (ซึ่งเป็นสถานการณ์ที่รุนแรงกว่าโดยเจตนา
เพื่อยืนยันว่าฮาร์เนสไม่ล้มง่ายเกินไป) **ยังไม่เคยพิสูจน์จริงบน `windows-latest` runner ของ
GitHub เอง** — ควรติดตามผลรัน CI จริงหลัง merge ก่อนปิดตั๋วนี้สนิท

**ข้อเสนอถ้ายังเจอ flake บน CI จริงหลัง merge**: (1) เพิ่ม `_wait_until_ready` deadline ต่อ (ไม่มี
เพดานบน "ถูกต้อง" ตายตัว เพราะมันไม่กระทบความเร็วของรันที่ผ่านปกติเลย) หรือ (2) ถ้าเกิดขึ้นบ่อย
ให้สงสัยว่ามีอย่างอื่นบล็อกจริง (เช่น antivirus ของ runner, resource limit ของ GitHub Actions)
ไม่ใช่แค่ CPU contention ธรรมดา

## พิสูจน์ว่าเทสต์ยัง non-vacuous (ย้อนกลไกจริงใน `server.py` ชั่วคราว แล้วคืนกลับ)

สคริปต์ throwaway (`nonvacuous_proof.py`, ไม่ commit เข้ารีโป) `mock.patch` `Handler._send()`
สามแบบ รันเทสต์เป้าหมายจริงในโพรเซสเดียวกัน แล้วคืนค่าเดิม:

| แบบที่ย้อน | เทสต์ที่ควรแดง | ผล |
|---|---|---|
| ตั้ง `close_connection=True` แต่ไม่ส่ง header `Connection: close` (AUDIT ข้อ 6 เดิม) | `TestBug011ConnectionCloseOn413` | **RED ตามคาด** — `assertIn(b"Connection: close", ...)` ล้ม |
| ไม่ตั้ง `close_connection` แม้ `body_bytes` ค้างอยู่ (เปิดช่อง smuggling) | `test_bug_011_smuggling_content_length_shorter_than_body_yields_one_response` | **RED ตามคาด** — เห็น 2 responses (`2 != 1`) |
| ปิดทุกคอนเนกชันเสมอ (over-eager "fix" ที่ทำให้ keep-alive ปกติพังไปด้วย) | `test_bug_011_keepalive_still_yields_two_responses_for_two_plain_gets` (เทสต์คุมกฎ) | **RED ตามคาด** — `2 != 1` |

หมายเหตุ: เทสต์ `test_bug_011_smuggling_chunked_with_nested_request_yields_one_response` **ไม่**
แดงเมื่อย้อนกฎข้อ 2 ข้างต้น เพราะมันถูกปกป้องโดยกลไกอื่น (`_begin_body()` ปฏิเสธ
`Transfer-Encoding: chunked` ด้วย 501 ก่อนถึง `_send()` เลย) — ตรงกับที่บันทึกไว้แล้วใน
`.claude/agent-memory/test-engineer/bug_011_body_caps.md` รอบ hardening ที่สอง (ชั้นป้องกันซ้อนกัน)
เลือกใช้ `content_length_shorter_than_body` แทนสำหรับ non-vacuous proof ข้อนี้เพราะมันพึ่งพา
กฎของ `_send()` โดยตรง ไม่มีชั้นป้องกันอื่นซ้อนอยู่
